# B5 · 容错、降级与自愈原理

> 本篇回答：**这套系统为什么敢说"自动化跑完了"，它靠什么防止"跑了个寂寞"**。
> 读者：所有要写步骤、调流程、看报告的人。**这是卷 B 里与实践最贴近的一篇。**

---

## 1. 头号敌人：假成功

> **核心心智模型 #1：动作执行成功 ≠ 业务生效。**

日志打印"点击成功/输入成功"只代表**控件被操作了**，不代表 UI 真的响应了。绝大多数疑难 bug 都是假成功。

### 1.1 三种典型形态

| 模式 | 症状指纹 | 根因 | 修复范式 |
|---|---|---|---|
| **A · 命中展示层** | 日志成功但界面无变化；命中控件 `controlType=Text/TextBlock`、`IsKeyboardFocusable=False`、无 Invoke/Selection/Value/Toggle 任一 Pattern | 评分命中了**只读显示层的文字**，而非真正可交互控件 | 补真实可点击目标，或改用 `click_relative_region`；评分里降权纯展示型控件 |
| **B · 输入未提交** | 输入那步"成功"，但下一步依赖该值的操作失败 | 值写入了控件但**未失焦/未回车**，程序未提交 | 配 `postInputKeys: {TAB}` 或 `{ENTER}` 强制提交与失焦 |
| **C · 错窗口** | 相对区域点击落到主窗口（rect ≈ 全屏）而非目标弹窗 | 空标题 WPF 主窗评分过宽，被当成候选弹窗 | 前台窗口优先；空标题窗口只在"确为前台"时兜底；收紧标题匹配评分 |

### 1.2 首因滞后（最重要的排障直觉）

> **报错步往往是连带受害者，不是首因。**

`step_39` 报错，真因常在 `step_36 → step_37` 的某个假成功。定位时必须**回溯到第一个"界面没按预期变化"的步骤**，而不是在报错步上打补丁。

## 2. 第二道防线：`continueWhen` 状态校验

### 2.1 原理

每个动作执行后，可以选择等待 UI 达到某个状态才算成功。合法条件：

```
exists / present / visible / enabled / gone /
nonempty / non_empty / value_equals / toggle / checked / toggle_state
```

例：点击"计算"后等待 `progressWindow gone`；输入后等待 `value_equals <输入值>`。

### 2.2 自动值断言（及其陷阱）

执行器对输入类动作会**自动生成 `value_equals` 值断言**（防假成功），但有些控件即使动作成功也**读不到值**，断言必然**假失败**：

| 不可读值控件 | 原因 |
|---|---|
| `PART_ContentHost` | WPF TextBox 内部编辑宿主（Pane/ScrollViewer），自身无 ValuePattern，父链也常读不到 TextBox 值 |
| `PART_DropDownButton` | 下拉框展开按钮，无 ValuePattern |
| `Text` / `TextBlock` 标签 | 读到的不是输入框的值 |
| 无 `label_text` 消歧的裸 `textbox` | 目标可能是多个同名输入框之一，读到的是错误/离屏控件 |

**处理**：自动值断言前先判断控件是否"可可靠读值"，不可读则**跳过自动值断言**（动作本身成功即视为通过）。判定函数：`_is_unreadable_value_control` / `_is_internal_content_host_control`。

> 📌 这条修复同时解决了一个性能问题：此前每次续跑等待都重新做一次全量定位，单步被拖到 **60–90 秒**。

### 2.3 幂等：`precondition`

执行**前**求值，满足则跳过动作。仅对**显式配置**的步骤生效、仅对实现 TogglePattern 的控件有效。
典型：`{"condition": "toggle", "expected": "off"}` → 已勾选就不再点。

配合 `check_all_toggles` 的**双保险**策略（物理点击 → 未翻转则程序化 `Toggle()` 收敛），共同保证勾选类操作可重复执行。

## 3. 分级降级：从精确到粗糙

> **心智模型 #4：定位是分层降级的，越靠后越脆。**

### 3.1 定位层面的四级（L1→L4）

| 级别 | 手段 | 可靠性 |
|---|---|---|
| **L1** | 复合精确定位（`automation_id,control_type` / `name,control_type` …） | ✅ 最强 |
| **L2** | `ui_path_search`（路径尾部对齐） | 中 |
| **L3** | `template`（图像模板） | 弱（像素像 ≠ 身份对） |
| **L4** | `coordinate`（坐标） | ❌ 最脆 |

**原则**：命中非 L1 即视为**退化**，应触发反馈记录与自愈学习，**而不是静默通过**。

### 3.2 执行层面的完整链路

（详见 A3 §3.3，此处只列降级顺序）

```
precondition 跳过判断
  → [可选] 模板优先 preferTemplate
  → run_action_step  +  重试 retryCount
  → fallbackChain（内含 L1→L4 各级备用定位）
  → 模板兜底 fallbackTemplate（onError=fallback）
  → AI 视觉介入（可选开关）
  → 仍失败：按 onError 决定 stop / continue / ask
```

**每一步都有"不可能三件套"在把关**：降级成功≠业务生效，所以降级恢复后**仍要过 `continueWhen`**。

## 4. 刻意不静默跳过的地方

自动化系统最容易出的工程问题是"该报错的地方没报错"。本项目明确反其道而行：

| 场景 | 处理 | 行号 |
|---|---|---|
| `script` 步骤**未绑定执行函数** | **记 `failed`**（除非显式 `optional` 才记 `skipped`） | L1885–1895 |
| 未知 `actionType` | 记 `skipped` **并写日志**（不无声略过） | L2015–2016 |
| AI 介入后**无 `continueWhen` 校验结果** | `aiInterventionUnverified = True` + **raise** | L1969–1975 / L1997–2002 |
| 同一 child 被多个流程包引用 | 第二次记 `skipped`「重复引用已跳过」，防二次点击 | L1862–1874 |
| 校验发现控件不在 `controls` 清单、占位值未填、method/value 段数不符 | **保存前就报错**（不允许带着问题入库） | `wt_flow_validation` |

> 📌 一句话：**宁可显式失败，不可隐式通过。**

## 5. 反馈闭环：从"跑完"到"越跑越准"

### 5.1 写回流程定义

`_write_feedback_to_flow(context, step_id, feedback_data)` 把降级恢复写**回流程定义**：

| 反馈类型 | 触发时机 | 载荷 |
|---|---|---|
| `fallback_recovery` | 降级链某一级成功 | `fallbackLevel`、`originalError` |
| `fallback_template_recovery` | 模板兜底成功 | `fallbackTemplate`、`originalError` |
| `step_failure` | 步骤最终失败 | 失败信息 |

执行上下文携带 `flowDefinitionPath` / `runId`，结果汇总进 `feedbackHistory`，形成**运行 → 反馈 → 优化定义**的闭环。

### 5.2 自愈式选择器

```
detect_healed_locator()  发现降级命中（priority > 0）
        ↓
record_self_heal()       持久化 override 到 self_heal_store.json
        ↓
下次运行该控件时 priority 提到 0（首选），逐步收敛
```

**配套的执行期行为**：失败时 best-effort 调用 `_AUTO_CAPTURE_TEMPLATE` 把当前控件区域截图存档（`auto_captured/<窗口>/<控件名>.png`），使下一次运行多一条模板兜底路径。

> ⚠️ 自动替换模板有安全阀——`images_are_similar()` 的 pHash 判定（卷 B4 §3.4）。**宁可不更新，不可把错误截图盖掉可用模板**。

## 6. 重试策略的位置感

| 层 | 机制 | 参数 |
|---|---|---|
| 动作层 | `_run_action_step_with_retry` | `retryCount` / `retryInterval`；`total_attempts = retryCount + 1` |
| 等待层 | `_wait_for_continue_when` | `timeoutSeconds`（动作默认来自 `wt_action_defaults`，如 `click`: 2.5 s、`waitAfter`: 0.12 s） |
| 退化层 | `fallbackChain` | 逐级放宽 |
| 策略层 | `onError` / `stepPolicy.onFail` | `continue` / `retry` / `fallback` / `stop` / `ask` |

> ⚠️ 已知技术债：`stepPolicy.maxRetries` 目前经 `sleep_seconds()` 强转使用，**语义错配**（数值恰好可用），待修。

## 7. `onError` 的语义陷阱（排查必读）

| `onError` | `stepPolicy.onFail` | 报告里的表现 |
|---|---|---|
| `stop`（默认） | `abort` | 步骤 `failed`，流程中止 |
| `continue` | `skip` | 步骤 **`failed`**，但**流程继续往下走** |
| `fallback` | `fallback` | 尝试模板兜底 |
| `retry` | `retry` | 重试 |
| `ask` | `ask` | 触发 AI / 人工介入 |

> 💡 **看到"流程报成功但中间有 failed 步骤"** → 先查是不是 `onError: continue`。这不是 bug，是设计。

## 8. 稳定性是有代价的

| 得到了 | 付出了 |
|---|---|
| 防住了大部分假成功 | 步骤定义变复杂（要配 `continueWhen` / `precondition` / `fallbackTemplate`） |
| 能在属性漂移后继续跑 | 评分表难调，改动面广 |
| 失败即可复盘 | 日志与报告体积大，需要工具读（`logs/last_run_report.json`） |
| 换环境自动降级 | 降级掩盖问题——**必须靠"退化告警"意识去盯报告里的 `fallbackUsed` / `fallbackTemplateUsed`** |

> 📌 **给使用者的一句话**：别只看"成功/失败"，要看**走了几级降级**。长期靠 L3/L4 命中的步骤，本质是"还没修好"，应该回到卷 B3 把它修回 L1。
