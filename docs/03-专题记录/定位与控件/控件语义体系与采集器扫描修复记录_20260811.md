## 1. 控件语义体系：UIA Name 与真实功能解耦

### 1.1 背景

WPF 按钮的 UIA `Name` 是 **SVG path 数据**（如 `M19/M18/M3/M6/M20`），与实际功能（添加/导入/编辑/删除）不匹配。**不能修改控件原始名称**（会破坏定位器），需要附加真实操作语义。

### 1.2 functionText：真实功能名

- **来源**：`helpText`（来自本地化资源）携带真实语义。
- **提取**：`_extract_functional_name`，过滤 `radxxx` 噪声、`pid/path`/SVG path 片段，截断 30 字符。
- **显示优先级**（`_display_control_name`）：`functionText > savedControlName > suggestedControlName > displayName`。

### 1.3 运行时消歧（采集 + 执行两侧）

- **定位方法**：`help_text` 定位器方法。
- **评分加分**：`get_control_definition_match_score` 中 helpText 匹配 +12。
- **同定位器消歧**：`_disambiguate_duplicate_locators` 用 `name / label_text / found_index` + `help_text` 分量区分多实例。

### 1.4 验证

重采的两个文件（`20260810_170157_window_导入及配置元素1_control_map.json`、`20260811_155647_window_control_发送综合计算_map.json`）确认优化生效，M 系列按钮语义正确。

## 2. 批量刷新步骤定位（编辑器）

**目的**：老流程包中已绑定步骤的定位信息，按 automationId 从合并后的控件总库匹配最新定义，一键同步全部已绑定步骤。

- `_extract_step_control_aid`：从步骤 inspectData 或 targetValue 首段提取 aid。
- `_pick_library_match`：同 aid 多实例时用 `labelText / relatedLabelName → uiPath` 判别，与合并工具 `_discriminator` 顺序一致。
- `_apply_library_definition`：幂等覆盖 `targetMethod / targetValue / helpText / functionText`。
- 入口：编辑器「批量刷新步骤定位」按钮（`bg="#bfdbfe"`）。
- **实测 5 场景 PASS**。

## 4. 采集器树采集卡死：根因调查

### 4.1 现象

开启树采集后，采集器窗口被系统标记"未响应"，目标软件（Meteodyn Universe）表现也卡。

### 4.2 调查过程与关键证据

| 证据 | 结论 |
|---|---|
| 采集器进程 `build_control_map_library.py` 窗口 SendMessageTimeout 超时，dwm ghost 窗口标题带 **"(未响应)"** | UI 线程彻底挂起，非"正常慢" |
| CPU **0%**（非忙等）、status running | 主线程阻塞在**同步对象等待**，不是计算 |
| `_hover_monitor.log`：BFS 卡在 **count=1000**（19:11:31 后 10 分钟无进展）；历史 **16:45/17:55 两次卡在 count=800** | 反复出现的 UIA 遍历中途阻塞 |
| 目标软件 `MUPSmartClient.exe` CPU **44%**、内存 **927MB** | 目标进程正忙，UIA Provider 应答延迟 |
| 目标软件进程名是 `MUPSmartClient.exe`（不含 Meteodyn/Universe 字样） | 按名字搜索易漏，需按 exe 路径匹配 |

### 4.3 根因

1. **扫描在主线程同步执行**：`_run_scan` 直接调用 `build_control_map_payload`，大窗口遍历期间整个窗口不响应（"未响应"）。
2. **UIA COM 调用无超时**：BFS 遍历对目标进程发 UIA 调用，目标进程忙时不返回 → 调用无限挂起。Python 层的 `scan_timeout_seconds` 检查只在**每轮循环迭代间**执行，程序卡在调用里时永远执行不到。

## 5. 采集器扫描修复：后台线程 + 取消

### 5.1 改动清单（build_control_map_library.py）

| 函数 | 改动 |
|---|---|
| `_walk_raw_view_bfs` / `_walk_wrapper` | 加 `cancel_event=None` 参数，BFS/DFS 循环内检查取消标志 |
| `_scan_single_backend_payload` / `build_control_map_payload` | 加 `cancel_event` 穿透；取消时**跳过全部补采**（探针 / uia_tree_dumper / 标签伴随），`scan_meta["truncation"]` 标 `cancelled` |
| `_run_scan` | 改为启动**后台 daemon 线程**（含 `pythoncom.CoInitialize`），主线程立即返回 |
| `_run_scan_worker`（新增） | 后台线程执行扫描，结果/异常经 `root.after` 交回主线程 |
| `_on_scan_finished`（新增） | 主线程完成回调：更新树/按需保存/恢复窗口；**中止时不自动保存** |
| `cmd_cancel_scan`（新增） | 置位取消事件 + 状态提示 |
| `_recover_ui_after_cancel_stall`（新增） | **兜底**：中止后 15 秒线程仍未返回则恢复界面按钮（可关窗口重开，不再只能强杀） |
| `_set_scan_ui_busy`（新增） | 扫描期间禁用两排操作按钮，仅保留「中止采集」 |
| UI | button_row1 新增「⏹ 中止采集」按钮；`__init__` 新增 `_scan_running / _scan_cancel_event / _scan_cancel_btn / _scan_disabled_widgets` |

### 5.2 验证结果

- Python 3.8 + 3.11 语法通过。
- **398 个测试全部通过**（无回归）。
- 取消机制 3 场景实测：
  - 正常扫描（不取消）：2.2s 完成，124 控件，无 truncation。
  - 0.3s 时取消：0.3s 截断返回，保留 18 个控件，`truncation.cancelled=True`。
  - 预置取消：0.06s 立即返回（仅根节点）。
- GUI 冒烟：按钮/状态变量/busy 切换正常。
