## 2. 主力采集器 `build_control_map_library.py`（9 623 行）

### 2.1 能力

- 用 pywinauto `uia` 后端遍历目标窗口控件树，输出控件库 JSON；
- 为每个控件**生成定位推荐**（`build_locator_recommendation`，见 B3 §3）；
- 评估控件"是否值得入库"（`assess_control_automatability`）；
- 生成补充校验项（`build_aux_checks`）；
- 采集期交互：`_ScanProgressOverlay`（扫描进度浮层）、`_TaskbarProgress`（任务栏进度）、`_play_notify_sound`（提示音）、`_paint_button`。

### 2.3 采集侧的过滤与消歧规则（重要）

| 规则 | 位置 | 说明 |
|---|---|---|
| **剔除无价值容器** | L516 / L526 | 既无 `automationId` 又无 `name`、且 `controlType` 属于无意义类型；或 `custom` / `pane` / `group` 且无 `automationId` → 不入库 |
| **超长/垃圾 name 过滤** | L389 | name 是 SVG path 几何数据、超长乱码、长度 > 80 → 置空 |

| **PART_ContentHost 折叠** | L977–982 / L4227 / L4319 | 折叠进父 TextBox（`foldedIntoParent`），单独入库只会带来不唯一 id 的冗余控件 |
| **下拉控件提示** | `_DROPDOWN_AUTOMATION_ID_HINTS`（L3230） | 识别 `dropdownbutton` / `combobox` / `combo` |
| **labeledBy 探测** | `_read_labeled_by_info` / `_LABELED_BY_PROBE_TYPES` | 对特定控件类型补读 `labeledBy` |

## 3. 三路外部采集适配器

> 定位：**可选补充**，不 import、不改默认链路。源码浅克隆在 `vendor/`（`.gitignore` 忽略）。

| 路 | 项目 | 协议 | 主要用途 |
|---|---|---|---|
| 自有 | pywinauto（`build_control_map_library.py`） | 进程内 | **主力**，全量采集 |
| 补充 1 | **uia-peek**（`vendor/uia-peek`, MIT） | HTTP `:9955` | 按坐标/焦点 peek 祖先链；可选 SignalR 录制键鼠事件流 |
| 补充 2 | **axe-windows**（`vendor/axe-windows`, MIT） | CLI + C# bridge | 补充 **Control Pattern**（Invoke/Value/Toggle/Selection） |

### 3.1 `uiapeek_client.py`

| 函数 | 作用 |
|---|---|
| `ping(base_url, timeout)` | 探活 |
| `peek_at(x, y, ...)` / `peek_focused(...)` | 按坐标 / 按焦点取祖先链 |
| `bounds_to_rect(bounds)` | 边界转换 |
| `node_to_control_definition(node, window_title, framework_id, depth, index, ...)` | 节点 → 控件定义 |
| `chain_to_payload(chain, source_label="uia-peek")` | 链 → payload |
| `save_payload(payload, control_map_dir)` | 落盘 `*_{uiapeek}_control_map.json` |
| `capture_at(x, y, save=True, ...)` / `capture_focused(...)` | 一站式采集 |
| `record_events(duration_seconds=10, ...)` / `recording_events_to_payload(events, ...)` | 录制事件流转 payload |

### 3.2 `axewindows_client.py`

| 函数 | 作用 |
|---|---|
| `find_cli_exe()` / `find_bridge_exe()` | 定位 `AxeWindowsCLI.exe` / C# bridge 可执行 |
| `bridge_element_to_control_definition(elem, ...)` / `bridge_json_to_payload(doc)` | bridge 模式转换 |
| `scan_process(pid, hwnd=None, output_dir=None, cli_exe=None, verbosity="verbose", ...)` | CLI 模式扫描（产出 `.a11ytest`） |

### 3.3 统一入口

```bash
python tools/external_capture/capture.py {uiapeek|axewindows} ...
```

### 3.4 ⚠️ 关键事实（别用错）

> **Accessibility Insights for Windows 的底层就是 Axe.Windows。但 Axe.Windows 的 Scan API 只返回"触发无障碍规则的元素子集"，不是整棵 UIA 树**（Live Inspect 才扫全树）。

所以 Axe bridge 快照的控件数偏少（约 59）是**正常的**——全量控件库仍应以自有 pywinauto 采集器为准，Axe 的价值只在**补充 Control Pattern**。

## 5. 蓝图 → 流程包：`tools/generate_flow_package.py`

把"MUP 手册里的合规操作步骤"自动变成可运行的 `flow_definition_*.json`。

| 函数 | 作用 |
|---|---|
| `load_catalog(path)` | 加载标准控件目录 |
| `build_source_info_catalog(aid)` | 按 automationId 建索引 |
| `build_control_from_catalog(aid, cat_ctrl, window_title)` | 目录条目 → 控件定义（含完整 `inspectHints` / `controls` / `actionConfig`） |
| `pending_control(step, idx)` | 生成 `PENDING_CAPTURE` 占位步骤 |
| `build_step(blueprint_id, step, idx, cat_map)` | 构建单步 |
| `generate(blueprint_path, cat_map)` | 生成流程包 |

**核心设计**：内置 **`SYNONYMS` 词表**把蓝图的中文业务名（如"新建风机类型按钮"）映射到标准库的 `automation_id`。

- 匹配到 → 输出 `click` + 完整定位信息；
- 未匹配 → 输出 `PENDING_CAPTURE` 占位步骤（`click_relative_region` / `type_text_relative` / `select_dropdown_item_runtime` + 模板兜底），由用户实时抓取后回填。

用法：`python tools/generate_flow_package.py <blueprint_id>... [--all]`

> 📌 输出的独立文件用 `WT_Flow_Editor` 打开，**保存时自动 `sync_flow_package_registry`** 同步进注册表，无需手改大文件。

## 6. ⚠️ P1 已知断点：采集落盘 ≠ 合并读取

| 环节 | 路径 |
|---|---|
| 采集落盘 | `build_control_map_library._save_control_map_payload`（~L1281）及 `tools/external_capture/*` 各适配器 → **`control_maps/` 根目录** |
| 合并读取 | `merge_standard_control_library.load_all`（L35–36）→ **只 glob `recordings/*_control_map.json` 与 `library/library_*.json`** |

**后果**：新采集的库**不会进入标准库合并流程**（现有 `standard/` 有数据仅因历史文件被手动搬进子目录）。

**但流程转换匹配不受影响**：`flow_recorder_converter._load_control_map_definitions`（~L234）用 `os.walk` 递归，能读到根目录及所有子目录。断点只在"合并 → 标准库"这条支线。

**修复（二选一即可闭环）**：① 让采集器直接落 `recordings/`；② 让 `load_all` 改为 `os.walk` 递归。

## 7. InterestAreas 同名按钮按节点消歧（典型案例）

这是"采集侧+合并侧+对话框去重"三处必须同步改动的典型案例，值得完整记住。

**问题**：各节点（测风点/风机/结果点/绘图…）共用同一套图标按钮 `InterestAreas_Button_Add/Edit/Delete/Import/ToggleTileState`，`automationId` 相同、UIA `name` 是 M6/M19/M20… 的 SVG path、功能语义只体现在 `helpText` 或面板标题上。

**根因链**：

1. 采集端 `_extract_panel_title` 取"父容器内**第一个**非 SVG 短文本兄弟"——而 Edit/Delete/Import 的同父容器里还有**字段标签**兄弟排在前面，取到了错误标签（如"载入/计算尾流效应/类型"）；
2. 合并工具 `_discriminator` 读 `labelText` 分桶 → 没按节点分桶；
3. **「合并入库」对话框走的是独立去重路径** `_merge_dedup_key`（`build_control_map_library.py`）与 `control_live_detector._build_dedup_key`，键为 `(aid, automationId, controlType, name)`；各节点按钮 `name` 为空 → **8 个节点键完全相同被误并为 1 条**。这就是"重跑合并入库又没了"的真正丢失点。

**修复范式**：

| 层 | 措施 |
|---|---|
| 采集端 | `_extract_panel_title` **优先返回 `automationId=InterestAreasView_Tile_Header` 兄弟的 name**（权威面板节点名），找不到才回退旧逻辑 |
| canonical 合并 | `normalize_control` 对 `InterestAreas_Button_*` 用该 `panel_title` 统一覆盖 `relatedLabelName` / `labelText`；无 TileHeader 时回退 `targetValue` 第 3 段节点名 |
| 对话框去重 | 三种去重模式（`aid` / `uiPath` / `name+ct`）**均追加 `"ia:<节点>"` 区分符**（优先 TileHeader → labelText/relatedLabelName → 兜底 rtv 第 3 段） |

> 📌 **教训**：新增字段或改消歧逻辑时，**采集端 / canonical 合并 / 对话框去重 三处必须同时改**，否则会出现"命令行合并好了、对话框又没了"的鬼打墙。

## 9. 资产维护纪律

| # | 纪律 |
|---|---|
| 1 | **新增字段必须三路同步**（自有采集器 / uiapeek / axewindows）+ 同步 `merge` 工具，否则合并时**静默丢字段** |
| 2 | 版本升级后**必须重新采集**并回归；不要指望旧库跨大版本可用 |
| 3 | 改消歧逻辑时，采集端 / canonical 合并 / 对话框去重**三处同时改** |
| 4 | 新增模板后确认 `templates_index.json` 已更新（否则索引扫不到） |
| 5 | 定期跑 `run_merge` 并看 `standard_catalog_mismatch_report.json`，把低权威项补抓 |
| 6 | 采集目标程序以管理员运行时，采集器也要提权（Axe 侧有 `_run_elevated_capture`） |
