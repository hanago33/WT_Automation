### ❌ P0③ `WT_Flow_Editor.py` 删除路径改用 `_sourceIndex` — **不完整，且引入数组错位（阻塞项）**

`delete_selected_controls`（L5078-5205）中共有 **4 处**使用"选中项下标"，本次只改了 **1 处**：

| # | 位置 | 用途 | 状态 |
|---|---|---|---|
| 1 | L5106-5119 | 组装确认框里显示的控件名 | ❌ 仍用显示位置 → **弹窗显示的名字与实际被删的不是同一个控件** |
| 2 | L5134-5153 | 收集 `deleted_keys`（驱动 `_mark_flow_controls_source_deleted` 标记所有 `flow_definition_*.json`） | ❌ 仍用显示位置 → **标记到错误的控件** |
| 3 | L5165-5186 | 从 `flatControls` 删除 | ✅ 已改用 `_sourceIndex` |
| 4 | L5190-5205 | 从 `controlDefinitions` 删除 | ❌ 仍是 `int(idx)`（显示位置） |

**为什么是阻塞项（不是"少修一处"那么轻）**

`flatControls` 与 `controlDefinitions` 是**按同一原始下标平行的数组**，证据有两处：
- L3615-3622：`for index, control in enumerate(controlDefinitions)` 内用
  `flat_controls[index]` 与之配对合并；
- L4698-4707：编辑回写时对两个数组使用**同一个** `source_index`，注释明写
  「回写到真实下标对应的 flatControls / controlDefinitions」。

因此 #3 删 `_sourceIndex`、#4 删显示位置时，两者几乎必然不同 →
**删除后两个数组不再平行**，其后每个控件的 flat 元数据
（`windowTitle` / `qualityTier` / `labelText` / `uiPath` / `recommendedTargetMethod|Value` / `auxChecks` …）
都会错配到别的控件，并在下一次保存时写回文件。

而"显示位置 ≠ 原始下标"是**默认情况**，不是边缘场景：
- `self.var_sort = tk.StringVar(value="质量优先")`（L3149，默认即排序）；
- `_get_filtered_controls()`（L3690-3731）**三个分支都会 sort**（L3716-3730）。

**与修复前对比**：修复前 #3/#4 都按显示位置删 —— 删错控件，但两数组**保持一致**；
修复后 #3/#4 取不同下标 —— **破坏了结构一致性**。故必须补齐才能合并。

**建议改法（一次解析、四处共用）**

```python
filtered = self._get_filtered_controls()
resolved = []
for idx in selected_indexes:
    src = None
    if 0 <= idx < len(filtered):
        cand = filtered[idx].get("_sourceIndex")
        if isinstance(cand, int):
            src = cand
    if src is None:
        try:
            src = int(idx)
        except (ValueError, TypeError):
            continue
    resolved.append(src)
```
随后 `control_names`(#1)、`deleted_keys`(#2)、`flatControls`(#3)、`controlDefinitions`(#4)
全部使用 `resolved`。这正是原审计报告"把 L4683-4696 的下标解析抽成共用函数"的建议。

### ⚠️ P0④ `wt_task_queue_window.py` 等长时补末行对比 — 症状已修，但代价与边界建议处理（非阻塞）

用自写脚本（假 Text 控件，300 行 tail 场景）实测四种情形：

| 场景 | 结果 |
|---|---|
| A. 等长 + 末行变化（滚动窗口推进） | ✅ 内容已跟上；**但绘制 = delete 1 次 + insert 300 次 → 每轮全量重绘** |
| B. 等长 + 完全相同快照（稳态） | ✅ 零绘制保持，原优化未退化 |
| C. 变长（追加） | ✅ 仅 append 1 行、无 delete，原优化未退化 |
| D. 等长 + 末行内容重复（假阴性边界） | ⚠️ **漏检**：`["x","y","same"]` → `["y","same","same"]` 时内容仍是旧值 |

- 场景 A 的代价值得注意：该函数存在的初衷就是避免全量重绘（docstring：
  「全量重绘会让日志区在用户拖动/选择时闪一整帧」）。当前实现等于把"冻结"换成了
  "每 2 秒闪烁 + 丢失文本选择"。
  **建议**：等长且末行变化时改为 `delete("1.0", "2.0")` 丢首行 + 追加尾行（O(1)），
  或比较尾部 k 行算出位移量后增量补齐。
- 场景 D：日志中连续相同的行很常见（重复的进度/步骤提示），此时面板会滞后，
  直到末行再次变化才刷新。
- **新增行为缺测试**：测试文件仅新增 `FakeText.get()`（+14/−0，无断言放宽，这点是对的），
  但没有为"等长位移应刷新"补用例。按仓库规矩（"新行为必须补断言"）应补一条，
  例如：渲染 `["a","b"]` 后渲染 `["b","c"]`，断言内容变为 `["b","c"]`。
