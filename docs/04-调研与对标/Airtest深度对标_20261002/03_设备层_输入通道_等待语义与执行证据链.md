# 卷三 · 设备层、输入通道、等待语义与执行证据链

> 覆盖模块：core/win/{win,screen,ctypesinput}.py、core/device.py、core/helper.py、utils/logwraper.py、report/report.py、cli/runner.py。
> 本卷回答三个问题：①Airtest 怎么"截"和"点"；②怎么让一次执行事后可完整审计；③哪些可直接给 WT 的输入通道参数化（影刃对标 P0-1）当第二参照。

## 1. 设备抽象（core/device.py，99 行）

`Device` 基类只约定接口签名：`uuid / snapshot / touch / swipe / keyevent / text / start_app / stop_app / shell / start_recording`，四个平台各自实现，上层 API（api.py）完全平台无关。核心思想与影刃"统一元素接口"、WT 的 `wt_flow_locator` 目标抽象同源：**上层语义不变，下层实现可换**。

对 WT 的直接意义：WT 只做 Windows，不需要四端抽象；但 `snapshot/touch/keyevent` 的"通道"维度可以照此抽象——**把"用什么后端截图、用什么通道输入"做成参数而不是函数名**（这正是影刃 P0-1 与 Airtest 此处的共同指向）。

## 2. Windows 设备层 win.py（739 行）逐项拆解

### 2.1 截图：mss 主路 + GDI 兜底 + 窗口裁剪（win.py:152-189, screen.py:15-65）

```python
def snapshot(self, filename=None, quality=10, max_size=None):
    if self.app:
        rect = self.get_rect(); rect = self._fix_image_rect(rect)
        monitor = {"top": rect.top, "left": rect.left,
                   "width": rect.right-rect.left-..., "height": rect.bottom-rect.top, "monitor": 1}
    else:
        monitor = self.screen.monitors[0]              # 全屏
    try:
        with mss.mss() as sct:
            sct_img = sct.grab(monitor)                # ① mss 快速抓取
            screen = numpy.array(sct_img, dtype=numpy.uint8)[..., :3]
    except:                                            # ② ScreenShotError → GDI 兜底
        return self.snapshot_old(filename, quality, max_size)
```

三层细节：

1. **按窗口 rect 抓取**而不是抓全屏再裁——少拷贝整屏像素；
2. `_fix_image_rect`（:183-189）做双屏虚拟屏偏移修正（mss 的 monitor 坐标含虚拟屏原点）；
3. GDI 兜底（screen.py）用 `GetWindowDC → BitBlt(SRCCOPY) → GetBitmapBits`，并处理**多显示器虚拟屏**（SM_XVIRTUALSCREEN=76 系列度量，:9-12）；
4. 另有 `focus_rect` 属性（win.py:593-601）：手动声明窗口边框厚度，截图后裁掉——解决"窗口装饰像素污染模板匹配"问题。

【WT 启示】WT 用 `pyautogui.screenshot`（底层 PIL ImageGrab，全屏 GDI 拷贝）是图像链路最慢一环；`mss` 是纯 pip 轻依赖（无二进制分发问题），且"mss 失败退 GDI"的双后端模式可原样照抄。`focus_rect` 对 WT 有直接场景：主窗口若带阴影/装饰边，模板截图时含边就会在窗口移动后失配——这正是 docs/05-调试案例/debug/debug-relative-region-offset.md 一类漂移问题的隐性来源之一。

### 2.2 DPI：手工系数的诚实处理（win.py:45-51, 609-623）

```python
self._dpifactor = float(dpifactor)   # 构造参数，注释明言 "no exact way to auto detect this value for a window"
def _windowpos_to_screenpos(self, pos):
    return (int((pos[0]+rect.left+focus[0]) * self._dpifactor), int((pos[1]+rect.top+focus[1]) * self._dpifactor))
```

不假装能自动检测，把系数做成连接参数，坐标换算集中在唯一一个函数里。WT 已有 `wt_dpi.py` 体系，对照价值在于：**换算只此一处、其余代码全部使用逻辑坐标**——检查 WT 是否存在散落的 DPI 乘法。

### 2.3 鼠标：插值移动 + 抖动反 hover（win.py:273-328）

`touch` 的完整动作序列：`duration/steps` 插值移动（默认 steps=1 即瞬移）→ 可选 `offset` 抖动（右下 1px 进再退回，:317-323，对付只认 hover 变化的 UI）→ `press → sleep(duration) → release`。`swipe`（:336-376）在终点**重复 move 10 次**再 release（:372-374）——确保终点 hover 状态被目标程序注册。

### 2.4 键盘双通道（win.py:191-271 + ctypesinput.py 全文）

| 通道 | 实现 | 原理 | 适用 |
|---|---|---|---|
| `keyevent(text)` | pywinauto `keyboard.SendKeys` | **虚拟键码**（VK_*），支持 `^a`、`%n`、`{ENTER}` 组合语法 | 常规应用、组合键 |
| `key_press(key)/key_release(key)` | ctypes `SendInput` + `KEYEVENTF_SCANCODE`（ctypesinput.py:246-257） | **扫描码**直发，绕过虚拟键映射层 | 只认 DirectInput 扫描码的程序（游戏、部分专业软件） |

扫描码表覆盖 84 个标准键 + 17 个扩展键（方向键/Insert/Delete 等需 `KEYEVENTF_EXTENDEDKEY` 标志，:9-28, 209）。注释明言设计动机："Some games use DirectInput devices, and respond only to scancodes, not virtual key codes"（:183-185）。

【WT 启示】这是 WT 输入通道参数化（影刃对标 P0-1）的**第二条实证路线**：影刃给的是 `simulate|clipboard|automatic` 三通道 + interception 驱动级；Airtest 给的是"虚拟键 vs 扫描码"同层双通道。WT 的 `send_keys`（pywinauto_recorder.player）只有虚拟键一通道；若 MUP/WT 软件某控件出现"SendKeys 无效"，扫描码通道是比"改用 UIA Value pattern"更接近物理键盘的下一步。参考代码见卷六附录 D。

### 2.5 剪贴板：锁重试与粘贴法（win.py:526-581）

`set_clipboard` 处理 `OpenClipboard` 错误 5（拒绝访问，剪贴板被其他进程锁住）：**sleep 0.1s 后重试一次**（:548-551）；`CF_UNICODETEXT` 写入；`paste()` 即 `^v`。注意 Airtest Windows 端的 `text()` **没有** IME 防线（直接 SendKeys）——对照影刃的 force_ime_ENG + 剪贴板粘贴全家桶（影刃对标 02 卷），WT 剪贴板输入落地时应取影刃方案、把 Airtest 的"锁重试"细节并入。

### 2.6 录屏（win.py:650-739 + aircv/screen_recorder.py 273 行）

ffmpeg-python 后端；**fps 硬上限 10**（注释："because of the recording effiency"，:688-693）；`max_size` 缩帧降载；录制期间警告"不要移动/缩放窗口"（区域锁定在首帧，:684-686）。对照影刃"30s 分段环形缓冲自动清理"（影刃对标 01 卷），Airtest 版更简单（单文件、max_time 到点即停）——WT 若做 P0-5 的执行录像，环形缓冲设计应取影刃、帧率/降载策略可参考 Airtest。

## 3. G 全局对象与图像资源解析（core/helper.py，259 行）

- `G` 用 metaclass property 实现 `G.DEVICE` 未连接时抛 `NoDeviceError`（:14-33）；`add_device` 按 uuid 去重、重复添加时替换并告警（:39-62）。
- **`G.BASEDIR` 图像搜索路径链**（cv.py:138-147）+ `using()`（helper.py:178-237）：`using("foo/bar.air")` 把该 .air 目录同时挂到 `sys.path`（可 import）和 `G.BASEDIR`（模板图可解析）——**脚本即包、图像随脚本走**，跨脚本复用流程时图像无需复制。WT 的 `templates_index.json` 全局索引模式更强（可集中管理），但"引用流程包时自动获得其图像目录"的体验值得在 WT 流程包（flow_packages）设计中对照检查。
- `delay_after_operation()`（:258-259）：`ST.OPDELAY=0.1` 全局操作后延时，收敛散落的 sleep。

【诚实评估】G 全局单例是 Airtest 为脚本式使用场景做的取舍，可测性差；WT 现有的 `configure_wt_projection_helpers` 依赖注入模式（wt_projection_helpers.py:38-74）在架构上**优于** G——不建议 WT 引入全局单例，仅借鉴 BASEDIR 式"路径解析链"的容错思想。

## 4. 执行证据链：logwrap → JSONL → HTML（utils/logwraper.py + report/report.py）

### 4.1 @logwrap：参数值审计（logwraper.py:95-164）

```python
def wrapper(*args, **kwargs):
    m = inspect.getcallargs(f, *args, **kwargs)     # ① 函数签名级参数快照
    m.pop('self', None); snapshot = m.pop('snapshot', False)
    fndata = {'name': f.__name__, 'call_args': m, 'start_time': start}
    logger.running_stack.append(fndata)             # ② 调用栈深度 → 报告层级
    try:
        res = f(*args, **kwargs)
    except Exception as e:
        fndata.update({"traceback": traceback.format_exc(), "end_time": ...}); raise
    else:
        fndata.update({'ret': res, "end_time": ...})
    finally:
        if snapshot is True: try_log_screen(...)    # ③ 步骤截图
        logger.log('function', fndata, depth=...)
```

- `inspect.getcallargs` 把**每个参数的实际值**（含模板对象、坐标）写入日志——影刃"每指令参数值快照"（影刃对标 01 卷五层证据链第 1 层）的轻量同构物。
- `running_stack` 天然形成调用层级 depth，报告按层级缩进渲染。
- 异常全栈进 `traceback` 字段，**报告以此判定步骤失败**（4.2）。
- `_dumper`（:37-54）：对象按 `to_json() → __dict__ → repr()` 三级降级序列化，保证任何参数都能落盘。

### 4.2 JSONL 单一数据源（logwraper.py:56-80）

每行 JSON：`{'tag': 'info'|'function', 'depth': int, 'time': float, 'data': {...}}`，逐行 flush。`G.log()`（helper.py:89-146）约定：**`data['traceback'] 非空 → 报告红字、步骤判败**；文本走 `log` 字段、可强制 `snapshot=True` 附截图。

### 4.3 HTML 报告（report/report.py，583 行）

`LogToHtml` 用 jinja2 渲染 log_template.html：`scale=0.5` 缩略截图、`timefmt` 时间轴、`static_root` 控制静态资源走 CDN 还是本地（导出模式）、`init_plugin_modules` 支持 Poco 插件扩展步骤渲染。**报告不回查数据库、不重算结果——log.txt 是唯一事实源。**

【WT 启示】对照 WT 的 `wt_run_reporting`（结构化 JSON 报告 + last_run_report.json）：

- WT 已领先：报告数据结构、fallback 统计、耗时汇总；
- 可借鉴三点：①**参数值快照**（WT 目前 _LOG_STEP 只记文本，失败时不知道"当时传了什么参数"——影刃 P1"每步输入输出快照"的 Airtest 版实现只需 `inspect.getcallargs` 一个调用）；②**traceback 非空即失败**的明确判定契约；③报告渲染与数据采集**解耦**（JSONL 先落盘、渲染随时重放）。

## 5. 等待与重试的边角机制

- `utils/retry.py`（63 行）：通用重试装饰器（次数+退避），设备连接等 IO 用。
- `OPDELAY`（helper.py:258-259）：所有 API 操作后的全局 0.1s 停顿，替代散落 sleep。
- `FIND_TIMEOUT=20 / FIND_TIMEOUT_TMP=3`（settings.py:22-23）：两档等待超时常量——"存在性检查用短档、主等待用长档"的语义区分。WT 的 `wt_action_defaults.py` 已有同类体系，对照校准数值即可。
