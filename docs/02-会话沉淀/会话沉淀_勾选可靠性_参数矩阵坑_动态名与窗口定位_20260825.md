## 一、表头 CheckBox 假成功 → CbValid 批量勾选（check_all_toggles）

### 1.1 现象与根因

step_22a「勾选-风向-热稳定度」日志报 success，但 UI 里 CheckBox 未勾选：

| 对照 | 22度 CbValid（成功） | 风向行头 CheckBox（假成功） |
|---|---|---|
| automationId | CbValid | 空 |
| 定位阶段 | fast 阶段 FindAll | fallback 整树枚举 |
| 点击行为 | toggle 0→1 | click_input 返回成功但 toggle 不翻转 |

根因两层：
1. **click 动作的成功语义 = "点击没抛异常"**，没有任何点后校验；
2. 表头 CheckBox 支持 Toggle/LegacyIAccessible 模式，但代码只有物理坐标点击。
   且程序化 `TogglePattern.Toggle()` 在该表头上**只改读数不落 UI**——物理点击和程序化
   切换对它都不可靠，此路不通。

### 1.2 最终方案：逐行勾选全部 CbValid（效果等同全选）

新增动作 **`check_all_toggles`**：
- `wt_flow_locator.py: check_all_unchecked_toggle_controls()`（约 :8578）——定位所有
  `automationId=CbValid` 的 CheckBox → 逐行读 ToggleState → off 则物理点击并校验，
  未翻转再走程序化收敛；禁用行跳过不计失败。**防假成功**：找不到目标抛 ValueError、
  有行勾不上抛 RuntimeError（步骤判失败可重试）。
- 复用三个助手（`wt_flow_locator.py:1881/1904/1925`）：
  `_toggle_fixup_desired_state`（从步骤 toggle precondition 推导点击后期望态）、
  `toggle_wrapper_via_pattern`（TogglePattern.Toggle，回退 LegacyIAccessible.DoDefaultAction）、
  `reach_wrapper_toggle_state`（有界收敛 ≤3 次）。
- `wt_flow_executor.py:1446` 分发分支；`configure_flow_executor(check_all_toggles=...)` 注入。
- flow 的 step_22a 控件改为 `风向行_CbValid_全勾选`（targetValue=`CbValid,CheckBox`）。

### 1.3 附带加固：click 点后校验（带 toggle precondition 才触发）

`click_flow_control` 中：若步骤显式配置 `precondition(condition=toggle)` 且指向被点控件，
点击后校验 ToggleState 是否翻转到期望；未达且点前可读时用 `reach_wrapper_toggle_state`
程序化收敛并记日志「点击后切换态未翻转，程序化Toggle兜底」。普通按钮零行为变化。

### 1.4 教训

- **"success" 日志 ≠ UI 生效**。对可切换控件必须点后读态验证，或像 check_all_toggles
  那样把"勾不上"判失败。
- 对个别不可靠的表头控件，绕开它（逐行操作数据行）比死磕它的交互方式更快。

## 二、四综合参数矩阵的连环坑与修复

### 2.1 stepMode 过滤失效的完整因果链（167 步乱局）

现象：展开成 90 步的功能跑出 167 步、create 行混入复制链、复制链定位"综合1"失败中止。

因果链：**编辑器保存剥离 stepTags → parameter_scan 的 stepMode 行级过滤静默失效 →
每行全跑 41 步模板**。复制链要求列表里已有"综合1"，而 create 行正在新建它 → 三连失败，
`step_copy_click` 的 onError 缺省 stop 终止整个运行。

### 2.2 修复清单

1. **硬失败防复发**：`parameter_scan.py: StepModeFilterUnavailable`（:30）——参数表含
   stepMode 列且有请求模式的行、但模板零 stepTags 时抛错；`WT_AUT_recorded._apply_param_table_expansion`
   让该异常穿透降级逻辑（其它展开异常仍安全降级）。启动即报清晰错误，不再静默全跑。
2. **编辑器根治不再剥 tag**：`wt_flow_editor_utils.normalize_step` 白名单重建时原样保留
   `stepTags`（与 fallbackChain 同类处理）。**从此可以用编辑器保存该 flow**（需重启 Launcher 生效）。
3. **占位符键大小写契约（重要隐性 bug）**：参数表读表器 `_snake_case` 把所有表头转小写
   （synthesisName→synthesisname）。流程占位符必须用小写键，camelCase 永远解析不出
   （曾致综合名/气象名以 `${...}` 字面量泄漏）。当前合法键：
   `stepmode/synthesisname/wohler/drawturbinetype/defaultturbine/weathername/cpversion/mettowername/refmast/refclimatology`。
4. **模板默认值兜底**：使用 `${...}` 的模板步骤自身 stepParams 种默认值（=当前硬编码名），
   scan 合并为「模板默认 + 行值覆盖」（parameter_scan.py:406）。参数表缺列时不泄漏字面量。
5. **双维过滤**：scan 已支持第二维 towerMode/towerTags（single/multi），mt_* 多塔步骤
   towerTags=['multi']，参数表全行 single 时多塔链路不执行（已搭好未启用）。
6. **三硬编码名参数化**：testMESO→`${stepParams.weathername}`（step_14/15）、
   Cp0.429→`${stepParams.cpversion}`（step_10）、M1→`${stepParams.mettowername}`（step_24a）；
   step_8/9/draw_select/draw_search 的风机类型同样参数化。参数表恢复
   defaultTurbine/weatherName/cpVersion 三列（create/copyfull 行填值，copy 行留空）。

### 2.3 排障方法论教训

- **先看数据再动手**：本次曾误删复制链（它其实是 copy/copyfull 的共用前缀），靠
  `flow_package_registry.json` 完整存有全部步骤才得以恢复。registry 是可靠的步骤定义备份源。
- **改 label 前先查录制实证**：海拔框 label 曾被我改成 '海拔'，实际录制显示其紧邻兄弟
  文本是单字符 '在'（"空气密度在[海拔]"语境）；'高度' 是另一行的标签。**'在' 是合法标签**。
- 单字符清洗规则随之撤回：`build_control_map_library.py: _clean_label_text`（:420）只丢
  纯标点/乱码/超长，**不按长度丢单字符**（会误删 '在' 这类真实标签）。

## 三、运行期控件名动态解析（${...} 进控件定义）

### 3.1 机制

跟随导入文件/设置命名的控件（如 testMESO、WT6250D220、综合3），不做逐次重采集，
改为名字写成 `${...}` 占位、运行时解析：

- `WT_AUT_recorded._ACTIVE_FLOW_CTX = threading.local()`（:896）：运行循环单步前放
  `{step_id, context}`，finally 清除，线程隔离。
- `_get_flow_step_resolved`（:899）：当前步骤在运行时，对 controls 列表做
  `_resolve_dynamic_value` 替换（返回副本，不污染 lru_cache 的原始定义）。
- 已接入 `configure_flow_locator` 与 `configure_flow_executor` 两处 get_step_definition。

### 3.2 两层解析的边界

- **文本层**（actionConfig.text/value）：由执行器 `_RESOLVE_DYNAMIC_VALUE` 解析，
  运行时始终接线。
- **控件名定位层**（controls[].targetValue/name）：靠上述 _get_flow_step_resolved。
  若该套未接线，占位符会以字面量参与定位而失败。
- 模板默认 stepParams 兜底后，两层在不走参数表时也解析到默认名，不会泄漏 `${...}`；
  但线性全跑语义是"一个综合跑满模板"，不是矩阵。

## 四、窗口定位可靠性：自动化自己的 Tk 进度窗抢前台（step_21 失败真凶）

### 4.1 现象与误诊史

单独跑 step_20/21：step_20 海拔键入成功，step_21 空气密度"未找到匹配控件"。
曾先后误诊为 label 错误、auxCheck 硬拒绝——均被证据推翻（auxChecks 是软加分不是硬拒绝）。

### 4.2 真凶（从日志实锤）

```
窗口枚举概要: windows=[{"title": "WT自动化 [第 1/4 步] 键入-海拔 [成功]", "class": "TkTopLevel"...}]
```

MUP 主窗标题为空，空标题回退只接受前台窗口；step_20 点击/续跑校验后**自动化自己的 Tk
进度窗抢了前台** → step_21 回退拿到自己的进度窗去定位 → 必然失败。昨天能过只是碰巧 MUP
在前台。更深一层：定位器自身的 `_enum_visible_mup_win32_windows()`（进程名枚举）
**运行中偶发返回空**（空闲实测能找到 MUP，运行中拿不到），这条路本身不可靠。

### 4.3 修复（权威主窗候选注入）

- `configure_flow_locator` 新增 `get_main_window_candidates` 注入点（wt_flow_locator.py:54/227）。
- fallback 候选顺序：**运行时主窗候选（find_main_windows）→ _enum_visible_mup 枚举 →
  前台（仅当非自动化自身窗口）**；`is_automation_window` 一律过滤 Tk 进度/监视窗。
- `WT_AUT_recorded._get_main_window_candidates`（:929）：复用预检同款
  `find_main_windows(MAIN_WINDOW_TITLE_RE, class_name_keywords=("MUPSmartClient",))`
  ——按进程名识别、UIPI 免疫，实测稳定返回 hwnd=985826 空标题主窗。
- 实测提供者输出：`hwnd=985826 title='' classMatch=True`（MUP 主窗）+ 标题窗各一。

### 4.4 教训

- 定位失败的排查顺序应是：**先看"窗口枚举概要"选的是哪个窗口**，再看控件匹配。
  选错窗口时控件信息再对也没用。
- 运行期窗口发现要用与预检同一套机制（进程名/UIPI 免疫），不要在定位器里再造一套枚举。
- 自动化的自有 UI 窗口（Tk 监视/进度窗）必须无条件排除出定位候选。

## 五、采集器 label 清洗边界（修正版）

`build_control_map_library.py: _clean_label_text`（:420）应用于 labelText/relatedLabelName
的主构建与序列化出口：丢弃纯标点/`_is_garbage_name` 乱码/超长(>80)。

**明确不做**："长度<2 丢弃"。MUP 存在单字符真实标签（海拔框紧邻标签 '在'），
按长度清洗会在重录时误删。测试见 tests/test_control_map_label_association.py::CleanLabelTextTests。
