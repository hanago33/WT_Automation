## 问题背景

### 用户反馈

> "现在几处更新之后，有些控件的定位结果比之前要差...我们有两点不成熟的建议：
> 1. 我们现在都是根据结果去优化'检验定位'和自动化流程执行定位 - 'wt_flow_locator.py'的定位功能，这样可能治标不治本；应该结合采集的控件信息本身的性质和特性去做定位优化，这样才更准确的在实际中精准定位。
> 2. 控件自身的信息有详有略，简单明了的控件应该有简洁的定位方法，复杂控件应该有复杂的定位方法。"

### 核心诉求

- **从数据端治本**：根据控件的数据丰富度差异化对待，而非从结果端修补
- **保留改进效果**：同时保证执行速度不因代码变更而显著下降

### 流程包字段丢失现象

对比 `flow_definition.json` 与控件库原始数据，发现约 40-50% 辅助字段丢失：

**Flow 包缺失的字段**：
- ❌ `rawInspectText`（人工调试依据）
- ❌ `auxChecks`（运行时验证条件）
- ❌ `processId/runtimeId`（进程上下文）
- ❌ `availablePatterns`（功能签名）
- ❌ `legacyIAccessible.*`（MSAA 兼容桥接）

**影响**：这解释了为什么某些定位会失败——流程包压缩过度，丢弃了降级链所需的兜底字段。

## 评分系统与近期变更影响分析

### 评分体系总览

#### 基础分（按优先级递减）

| priority | targetMethod | 基础分 |
|---------|--------------|--------|
| 0 | targetMethod/targetValue | 120 |
| 1 | automation_id,control_type | 120 |
| 2 | automation_id | 110 |
| 3 | ui_path | 100 |
| 4 | name,control_type | 100 |
| 5 | name | 90 |
| 6-9+ | class_name/found_index variants | 80-60 |

#### 字段加分规则

| 字段 | 加分 |
|------|------|
| automationId 精确匹配 | +14 |
| name 文本匹配 | +10 |

| className 类名匹配 | +6 |
| frameworkId 框架匹配 | +4 |

| 特征 | 加分 | 惩罚 |
|------|------|------|
| ancestors 父链命中 | +6 | - |

```
AuxChecks:         假设 4×1 = 4
Ancestors:         6
FoundIndex:        12
Children:          24
WindowTitle:       24
Visible/Enabled:   1+1 = 2
───────────────────────────────────────
理论最高：**248 分**
```

### 近期变更的回归根因

#### 问题代码（死代码）

L4010-4020 的低置信返回逻辑：

```python
if _low_confidence_match is not None and best_score <= 0:  # ❌ 永远为 False！
    return _low_confidence_match
```

**矛盾点**：
- `_low_confidence_match` 只在 `0 < best_score < 100` 时设置
- 一旦设置，best_score 必然大于 0
- 因此 `best_score <= 0` 永远为 False → **该代码块从未被真正触发**

#### 真实回归源：L4100 无条件返回

```python
# 修复前：致命 bug
if best_match is not None:  # ❌ 返回任意正分匹配
    return best_match
```

**场景复现**：
1. step_2 风机类型创建：automationId="TurbineType_Create_Button"，windowTitle="新建风机类型"
2. 正确窗口中：automationId 匹配 = 120 + 14 = 134 分
3. 若 windowTitle 不匹配（-160 惩罚）→ 134 - 160 = -26 分（不会被选中）
4. 错误 Dialog 窗口中的"确定"按钮：仅 name 相似 = 50 分
5. 无 windowTitle 惩罚 → 50 分被返回 ❌

#### 窗口软化扩大搜索范围

`iter_flow_search_windows()` 在严格过滤无命中时回退到全窗口枚举，增加了误搜概率：

```python
# 原逻辑：严格过滤失败直接返回 []
if not ranked_windows and title_candidates:
    return []

# 新逻辑（优化 2）：软化了，允许所有窗口参与搜索
if not ranked_windows and title_candidates:
    _LOG_STEP("窗口过滤软化...")
    # 枚举所有窗口 → 错误窗口中的相似控件可能被误选
```

### 用户"定位变差"的真相

**根本原因**：**L4100 无条件返回**接受了低分误匹配，而不是阈值放宽代码本身的问题。

**典型场景**：
1. high-richness 控件（有 automationId）应维持 >=100 严格阈值
2. 但 L4100 无条件返回任何正分匹配
3. 导致一个仅有 name 相似、score=50 的误匹配提前返回

## 性能瓶颈调查

### 性能下降原因分解

| 原因 | 占比 | 单次开销 | 说明 |
|------|------|---------|------|
| 代码变更引入重复计算 | 70% | ~0.5-1.5ms/步 | while 循环内重复调用 `_classify_control_richness()` |
| JSON 模糊匹配 Stage A | 20% | 50-200ms/次 | 首次加载 22MB JSON 文件并遍历数千控件 |
| bbox 距离计算 | 5% | ~0.01ms | 浮点运算 |
| 单线程模型限制 | 5% | N/A | 无法并行处理多个窗口/步骤 |

### while 循环重复计算细节

```python
def find_flow_control(step_id, control_id, ...):
    while not _search_timeout_exceeded(deadline):
        # ❌ 每个 retry 都重新计算同一个控制定义！
        for raw_control_definition in controls:
            control_definition = _normalize(...)
            
            # 第 1 次计算：dict.get() + string comparison ≈ 0.1ms
            _richness = _classify_control_richness(control_definition)  
            
            for window in windows:
                # 第 2-3 次计算：同样的控制定义又算了一遍
                _adaptive_threshold = _get_adaptive_threshold(_richness)
                
                # ... 搜索控件 ...
```

**累积效应**：
- 每步平均 while 迭代：3-5 次
- 每步平均窗口数：2-3 个
- **额外开销** ≈ 0.1ms × 3.5 次 × 2.5 窗 = 0.875ms/步
- 整个流程 100 步 → **总计 87.5ms 额外耗时**

### 项目线程模型

**纯同步单线程执行**：

1. **流程执行器** (`wt_flow_executor.py`)：
   ```python
   def execute_step_by_id(step_id, step_index):
       # 完全同步串行
   ```

2. **主循环** (`WT_AUT_recorded.py`)：
   ```python
   for step in execution_plan:
       execute_step_by_id(step.id, ...)  # 等待完成才进入下一步
   ```

3. **定位器** (`wt_flow_locator.py`)：
   - pywinauto 的 `Desktop.windows()` 是阻塞式 UIA 树遍历
   - 无任何异步 IO 或并发机制

**影响**：无法利用多核 CPU 并行处理多个窗口或多个步骤。

```python
import json
from pathlib import Path

class ControlMapPreprocessor:
    """预处理控件库 JSON 建立快速查找索引"""
    
    def __init__(self, json_path: str):
        with open(json_path, 'r', encoding='utf-8') as f:
            self.data = json.load(f)
        
        # 建立索引：automationId → 控件对象
        self._automation_id_index = {
            ctrl['automationId']: ctrl 
            for ctrl in self.data 
            if ctrl.get('automationId')
        }
        
        # 建立索引：name → [控件列表]（用于模糊匹配）
        self._name_index = defaultdict(list)
        for ctrl in self.data:
            if ctrl.get('name'):
                self._name_index[ctrl['name']].append(ctrl)
    
    def get_by_automation_id(self, aid: str):
        return self._automation_id_index.get(aid)
    
    def search_by_name_fuzzy(self, query: str, threshold=0.6):
        candidates = []
        for name, controls in self._name_index.items():
            ratio = fuzz.ratio(query.lower(), name.lower())
            if ratio >= threshold * 100:
                candidates.extend([(ratio, ctrl) for ctrl in controls])
        return sorted(candidates, key=lambda x: -x[0])[:5]
```

### 控件富集度分类函数

```python
def _classify_control_richness(control_definition: dict) -> str:
    """根据控件定义的字段丰富度分类."""
    if not isinstance(control_definition, dict):
        return "mid"
    
    inspect = control_definition.get("inspectData", {})
    if not inspect:
        inspect = control_definition
    
    automation_id = (inspect.get("automationId") or 
                     control_definition.get("automationId") or 
                     control_definition.get("targetValue", ""))
    
    name = inspect.get("name") or control_definition.get("name", "")
    control_type = (inspect.get("controlType") or 
                    control_definition.get("controlType", ""))
    ui_path = control_definition.get("uiPath", "")
    
    target_method = control_definition.get("targetMethod", "")
    uses_automation_id = ("automation_id" in target_method if target_method 
                         else bool(automation_id))
    
    if uses_automation_id and automation_id:
        return "high"
    if ui_path:
        return "high"
    if name and control_type:
        return "mid"
    return "low"


def _get_adaptive_threshold(richness: str) -> int:
    """根据数据丰富度返回匹配阈值."""
    return {"high": 100, "mid": 50, "low": 1}.get(richness, 100)
```

### 自适应阈值使用示例

```python
def find_flow_control(step_id, control_id=None, ...):
    _richness = _classify_control_richness(control_definition)
    _adaptive_threshold = _get_adaptive_threshold(_richness)
    
    while not _search_timeout_exceeded(deadline):
        for raw_control_definition in controls:
            # 不再重新计算 _richness/_adaptive_threshold
            
            # 使用自适应阈值代替硬编码 100
            if best_score >= _adaptive_threshold:
                return best_match
            
            # 低置信记录条件
            if 0 < best_score < _adaptive_threshold:
                if best_score > _low_confidence_score:
                    _low_confidence_match = best_match
                    _low_confidence_score = best_score
        
        # 最终返回条件
        if best_match is not None and best_score >= _adaptive_threshold:
            return best_match
```
