## 一、症状与表层根因：虚拟化下拉的 UIA 枚举死路

### 1.1 现象
新建气象数据流程 step_18（选择-日期时间）/step_20（选择-平均风速）/step_23（选择-风向）
连续失败。三轮日志一致：

```
下拉选项枚举进度: ... 候选窗口=3, raw探针=0, win32探针=0, sweep探针=0
流程控件定位耗时较长: step=step_18, control=dropdown_item, seconds=1.49, score=111, phase=fallback
运行时下拉项未命中且未枚举到候选项: ... wrapper=Popup|Window|(empty)
```

### 1.2 窗口收集不全（第一轮修复）
- 最初 `_collect_dropdown_windows` 只有 `Desktop.windows()` + desktop children，运行时只收集到
  主窗口（`候选窗口=1`），"导入时间序列文件"对话框和 WPF Popup 均未进列表。
- 修复：改为三路并集（按句柄去重）：`Desktop.windows()` → desktop 原始 children →
  `_enum_visible_mup_win32_windows()` + `_GET_MAIN_WINDOW_CANDIDATES()` 按句柄包装
  （即 `find_flow_control` 同源窗口收集，日志"采用运行时主窗口候选 4 个"的路径）。
- 结果：Popup 进列表（`候选窗口=3`），但 `raw探针` 仍 0 —— 选项不在树里，与窗口收集无关。

### 1.3 枚举剪枝 bug + 采集证据（第二轮修复）
- `_iter_dropdown_raw_view_candidates` 预过滤把"非 ListItem 中间容器"`continue` 掉，
  其子树选项永远遍历不到 → 修复为"非候选不 yield 但深入子树"。
- 采集文件 `scanMeta` 决定性证据：`rawTotalControls=4` vs `totalControls=424`
  （201 ListItem）→ UIA 只能看到 4 个控件，**选项是 win32/定点探针采到的**。
- 加 win32/MSAA 兜底 `_iter_dropdown_win32_text_candidates` → `win32探针` 仍 0
  （选项 `LegacyIAccessible.*` 字段全空，MSAA 树也没有）。
- 加"点扫掠"`_sweep_dropdown_option_by_point`（复刻采集器 `_realize_options_by_point_sweep`：
  物理移动鼠标触发 WPF 实体化 + `Desktop.from_point` 命中），修锚点
  （`GetWindowRect` 而非 UIA bounding box）与扫掠起点（anchor top 而非 bottom）。

**结论**：虚拟化下拉选项不在任何 UIA/MSAA 树中，枚举树的路从根上走不通。
但采集器能用"点扫掠"采到 —— 这是线索，不是根因。

## 二、真正的根因：流程定义缺 `label_text` 消歧（对比 step_9 成功范式）

### 2.1 用户关键提示
> "step_8-9 也是点击下拉框并选择候选项，怎么这两个步骤成功，但 step_16-25 同类型步骤失败？"

### 2.2 对比结论
同一 RPF 自绘框，控件定义差异：

| | step_9 选择-私有分组（成功） | step_18/20/23（失败） |
|---|---|---|
| action | `double_click` | `select_dropdown_item_runtime` |
| targetMethod | `class_name,label_text` | `name,class_name` |
| targetValue | `ListBoxItem,私有` | `DateTime,ListBoxItem` |
| labelText | `私有` | **空** |

step_9 的 notes 明示（2026-09-01 修复记录）：
> "原 class_name=ListBoxItem 太宽泛，**下拉弹出时误命中 Popup 窗口本身**导致双击未选中。
> 加 label_text=私有 硬性消歧（'私有'在 ListItem 子 TextBlock，locator 子文本匹配）"

step_18/20/23 缺的正是这步：运行时 ListItem 的 `name` 是类型名/空（采集文件
`name="MTD...MTDLocalizedEnumValue"` 同类），`name,class_name` 匹配不上 →
`find_flow_control` 回退误命中 Popup 窗口（`wrapper=Popup|Window, score=111`）→ 枚举死路。

### 2.3 修复（流程定义，与 step_9 完全同构）
`flow_packages/flow_definition_新建气象数据.json`：

```json
step_18 → targetMethod="class_name,label_text", targetValue="ListBoxItem,日期时间", labelText="日期时间"
step_20 → targetMethod="class_name,label_text", targetValue="ListBoxItem,平均风速", labelText="平均风速"
step_23 → targetMethod="class_name,label_text", targetValue="ListBoxItem,风向",       labelText="风向"
```

### 2.4 验证（真机）
```
[FlowLocator] 阈值放宽命中：step=step_18, ctrl=dropdown_item, score=36(threshold=50, richness=mid)
已直接点击下拉选项（目标控件即选项本身）: step=step_18, control=dropdown_item, text=DateTime, click=click_input
```
三个步骤均从"枚举失败"变为"直接点击选项成功"。

## 三、提速：auto-assert `nonempty` 对选项控件假失败

### 3.1 现象
消歧后点击成功，但每步仍 15s（step_18=15.29s / step_20=14.79s / step_23=14.89s）：
```
已直接点击下拉选项... text=DateTime
等待步骤续跑条件: step=step_18, phase=action, control=dropdown_item, condition=nonempty, timeout=3.0
[FlowLocator] ... 流程控件定位失败（反复 4 次，每次 ~1s）
步骤结束: step=step_18, status=failed, error=步骤续跑条件未满足: condition=nonempty
```

### 3.2 根因
`_resolve_continue_when` 为 `select_dropdown_item_runtime` 自动生成 `nonempty` 值断言
（Lesson I 模式）。但 ListItem 选项控件 `supportedPatterns=[]`、无 ValuePattern，
点击后**读不到值** → 断言必然假失败 → 反复定位轮询 + 超时。

### 3.3 修复
`wt_flow_executor._is_unreadable_value_control` 的 `unreadable_markers` 追加：
`listboxitem` / `listitem` / `menuitem`。动作成功（`direct_option_click` 已点击）即视为通过。

## 四·五、提速记录（第二轮：9.4s/步 → 预期 ~6.5s/步）

- **现象**：消歧 + auto-assert 豁免后 step_18/20/23 全部 success，但每步仍 ~9.4s。
- **耗时构成**：循环前 `_collect_dropdown_windows`（~6s，含两次全量三路枚举）+ `find_flow_control`
  label_text 全树扫描（~3s）+ 直点（~0.5s）。
- **修复**：`select_dropdown_item_runtime` 的 popup 合并改为"预收集已含 Popup 窗口
  （class/type 含 popup）时跳过第二次全量重收集"——三路收集含全桌面 UIA 枚举 +
  多次 ElementFromHandle，单次数秒，第二次纯属重复劳动（预收集已覆盖已展开的 Popup）。
- **剩余耗时**：`_collect_dropdown_windows`（~3s，必要）+ `find_flow_control` label_text
  全树扫描（~3s）。进一步提速需动 `find_flow_control` 内部（窗口候选按大小排序先扫
  Popup、label-rect 缓存、raw sibling 预过滤），影响全流程、风险较高，建议独立评估；
  或用采集文件选项坐标改 `click_relative_region`（方案 B，~1s/步，但需先验证风速/风向
  通道坐标对应，牺牲通用性）。

## 六、经验教训

1. **同流程内"同类步骤一成一败"是最高效的定位路径**：直接对比 step_9 vs step_18 的
   控件定义，差异即根因，胜过继续改引擎。
2. **RPF/MTD 自绘控件 `name` 是类型名/空时，`label_text`（子文本）消歧是必备手段**：
   `class_name,label_text = ListBoxItem,<中文显示文本>`，与 step_9"私有"完全同构。
3. **虚拟化下拉（Telerik/MTD）选项不在 UIA/MSAA 树中**：枚举树（Control/Raw/win32/MSAA）
   对这类控件从根上不可行；采集器靠"点扫掠 + 鼠标实体化 + `from_point`"才能采到
   （见 `build_control_map_library._realize_options_by_point_sweep`）。
4. **auto-assert 豁免必须覆盖无 ValuePattern 的选项控件**：ListItem/ListBoxItem/MenuItem
   点击成功后读不到显示值，`nonempty`/`value_equals` 断言必然假失败（拖慢 + 误报 failed）。
5. **原链路成功 ≠ 当前链路可复现**：原 `flow_definition.json` 的 dropdown_item 定义与当前
   几乎一致，差异在引擎变化；引擎失效时优先在流程定义上复刻"同流程已验证成功的步骤范式"。
