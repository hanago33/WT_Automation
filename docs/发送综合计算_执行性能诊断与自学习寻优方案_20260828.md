| **先做什么** | 阶段 1 的确定性数据补齐（33/19/15 组待补字段），收益最大、零引擎风险 |
| **预期** | 阶段 1 后 ~4 min；阶段 1-4 后 ~3 min 且方差显著压平 |

## 3. 根因分析

| 编号 | 根因 | 证据 | 代码位置 |
|---|---|---|---|

| **R2** | **19 / 52 步骤无 `automationId`** → fast 阶段无法用 UIA 原生 `FindAll(AutomationId)`，直接掉进 `descendants()` 全树 | `step_19` 定位失败耗时 10.35 s（整树 9.19 s）；`step_8`/`step_9`/`step_14`/`step_15` 等靠 `name,control_type` 匹配 | `wt_flow_locator.py:4090`（`build_fast_locator_queries`）、`:7408`（`window.descendants()`） |

**衍生结论**：R1（3 窗口）× R2/R3（全树）是乘性叠加——一个无窗口约束、无 aid 的步骤，最坏情况要跑 3 次全树扫描。这就是 `step_3` 能到 38.5 s 的原因。

> ⚠️ 但要注意 **"3 个候选窗口"不是必然付 3 倍代价**：`_find_flow_control_impl` 的 fast 阶段一旦
> `best_score >= 100` 就立即 `return`（`wt_flow_locator.py:7356`），**后续窗口根本不会被扫描**。
> 所以 3 窗口只在"前序窗口没命中"时才真正付出代价。
> → **R1 的正确解法是"让控件在第 1 个候选窗口内快速命中"，而不是"减少候选窗口数"**。
> 这正是 T1.4（父链 / label_text）的价值所在，也意味着 T1.4 的优先级高于原定的 T1.2。

## 3.1 补充调研：`windowTitle` 采集机制与「T1.2 作废」结论

> 背景：执行 T1.2 前需要确认"现有采集器能否采集到窗口标题"，调研后发现**原 T1.2 的前提不成立**，特此更正。

### 3.1.1 采集器**能**采集窗口标题（机制是通的）

| 环节 | 位置 | 说明 |
|---|---|---|
| 顶层窗口信息落盘 | `build_control_map_library.py:1537`、`:5047` | `targetWindow = {title, className, processId, handle, frameworkId}` |
| 每个控件条目附带 | `build_control_map_library.py:1534-1539`、`:6989-6990`、`:979-985`（缺失时回填） | `flatControls[*].windowTitle` / `windowClassName` |
| 由库生成步骤控件定义 | `build_control_map_library.py:3089-3097` | 生成的 `control_definition` 自带 `windowTitle` |
| 文件名即窗口标题 | `control_maps/library/library_<标题>_<framework>_controls.json` | 如 `library_地形_WPF_controls.json` → `targetWindow.title = "地形"` |

采集方式（**均无需改代码**）：

```powershell
python build_control_map_library.py                 # GUI 模式：选窗口 / 整树扫描 / 画框扫描
python build_control_map_library.py "窗口标题关键字"    # CLI：按标题关键字定位目标窗口
python build_control_map_library.py --foreground      # CLI：扫描当前前台窗口
```

### 3.1.2 但对本链路**无效**——四条互相印证的证据

| # | 证据 | 值 |
|---|---|---|
| 1 | **MUP 主窗口标题为空** | 日志：`[mup-preflight] 窗口健康检查通过，已置顶: hwnd=3016554 title= size=2560x1516` |
| 2 | **采集器对主窗口记为 `*`** | `control_maps/library/library_主窗口_WPF_controls.json` → `targetWindow = {"title": "*", "className": "", "processId": "", "handle": "", "frameworkId": "WPF"}` |
| 3 | **48 / 52 步的 uiPath 根是 `Window_Main`** | 逐条调用 `parse_uipath_root_segment` 验证，根段一律为 `Window_Main` |
| 4 | **`Window_Main` 被判定为主窗口根 → 标题强制为 `*`** | `GENERIC_MAIN_WINDOW_ROOT_NAMES = {"window","window_main","mainwindow","main_window"}`（`wt_flow_editor_utils.py:116`）→ `uipath_is_main_window_root()` 返回 True |

**运行时链路**（`wt_flow_locator.py:4931-4939`）：

```
uipath_is_main_window_root(uiPath) == True
    → control_window_title = "*"
    → 命中 {"*","__all__","__ALL__"} 分支
    → control_window_title = "" ; step_window_title = "" ; window_title_hint = ""
    → title_candidates = []
    → _wrap_win32_window_candidates(..., include_all=True)   # 枚举全部可见顶层窗
```

**复核结论（用项目自身函数逐条判定，非估算）**：

```
总步数 = 52
uiPath 根判定为主窗口根的步骤数 = 48
windowTitle 在运行时真正生效的步骤数 = 0
```

即：**包括 `step_3` 填的 `创建一个新建模`、`step_5` 填的 `主面板` 在内，整条链路没有任何一步的 `windowTitle` 在运行时起作用**。
链路里 19 步已成 `*` 正是 `normalize_window_title_for_uipath`（`wt_flow_editor_utils.py:157`）自动写入的结果。

> 该函数的注释本身就预见了这一点：
> "这类控件的 windowTitle 若写成控件库分类名……运行时按标题过滤必然 -160 判负，应视为伪标题并改为不约束。"

### 3.1.3 结论：T1.2 作废，工作重心转向 T1.4

| 原计划 | 修正 |
|---|---|
| T1.2「给 22 步补 `windowTitle`」→ 收敛到单窗口 | **作废**。填任何值都会被 `normalize_control_window_title` 改回 `*`，或被运行时清空 |
| 认为 R1 的解法是"减少候选窗口数" | **修正**。解法是"让控件在第 1 个候选窗口内快速命中"（见 §3 衍生结论的警示框） |
| T1.4（父链 / label_text）排第 4 | **提升为阶段 1 的最高优先级**（R1 的真正解药） |

**顺带发现的一处未接线的能力（不改代码则不可用，仅记录）**：
`iter_visible_top_level_windows()`（`wt_flow_locator.py:3757`）已经返回 `processName`（进程映像名），
但 `_wrap_win32_window_candidates`（`:3839`）只比对 `processId`（**数字字符串**），
而 `get_control_process_candidates`（`:3363`）又**刻意跳过纯数字**以免旧 PID 失效——
两者语义对不上，**"按进程名过滤窗口"这条线当前是断的**。若日后允许改代码，把 `:3839` 增加
`processName` 比对即可为整条链路提供一条稳定的窗口收敛维度（进程名 `MUPSmartClient` 跨运行不变）。

## 4. 自学习寻优：可行性判断

### 4.1 先给"路径"正名

> **能自寻优的是「定位路径」（locator route），不是「业务步骤路径」。**

- 流程里 52 步的**顺序是业务语义**（点综合 → 创建 → 命名 → 选机型 → 选气象 → 设参数 → 保存 → 发送计算），**不可重排、不可删减、不可并行**（单 GUI 线程 + UIA，并行必然互相踩踏）。
- 真正有优化空间的是「**每个控件是怎么被找到的**」：从哪个窗口找、沿哪条祖先链下钻、用哪个阶段命中。
- 这个问题恰好具备：**臂空间小（≤9）、反馈明确（命中/未命中 + 耗时）、试错成本可承受（失败可回退）** —— 适合做学习，但**不适合做探索性强的算法**（一次试错 = 一次全树扫描 = 最多 38 s）。

### 4.3 算法选型

本质问题 = **上下文多臂老虎机（Contextual MAB）**：

- **臂（≤9）**：`fast_aid_findall` / `fast_name_descendants` / `raw_view_findall` / `raw_view_bfs` / `descendants_full` / `label_to_input` / `tab_navigation` / `image_template` / `keyboard_nav`
- **上下文**：`(baseStepId, controlId, windowSig)`，其中 `windowSig = process + frameworkId + titleHash (+ towerMode 等状态特征)`
- **奖励**：硬约束 **不误点**；软目标 **p50 延迟**

**但第一阶段不要上 bandit**，理由：

1. 臂空间 ≤ 9，且绝大多数 `(step, control)` 只有**一个稳定赢家**，不存在真实多臂竞争；
2. 每次试验成本 **3~40 s**，探索极其昂贵；
3. 误点代价是**项目数据被写错**，不是"推荐不准"。

✅ **推荐形态：路由记忆 + 强校验 + 熔断降级（确定性贪心）**
第一次走全链并记录 → 之后优先按记忆走 → 校验失败立刻静默回退全链并降权 → 连续失败 2 次清除该路由。
这在效果上就是 bandit 的收敛态，但**可解释、可审计、无随机性、不放大误点风险**。

⚠️ **升级判据**：仅当某个步骤的记忆命中率**连续 5 次运行 < 90%**（说明存在真实多臂竞争，如该控件在不同界面状态下需走不同阶段），才对该步骤单独升级为 **UCB1 / ε-greedy**，准则用
`expected_cost = (1 − p) × penalty + p × p50`，且只接受 **`p ≥ 0.95 且 n ≥ 3`** 的臂作为首选。

❌ **明确不做**：

| 不做的方案 | 原因 |
|---|---|
| 强化学习 / 遗传算法 / AI 规划路径 | 不可复现、不可解释；试错成本（秒级~十秒级/次）不可承受；出问题无法归因 |
| 跨进程缓存 UIA wrapper 句柄 | 句柄每次运行失效。只能存**符号化路由**（窗口签名 + 祖先 automationId 链 + 控件身份 + 命中阶段） |
| 硬编码坐标替代定位 | DPI / 窗口尺寸 / 布局一变就全废 |
| 重排或删减业务步骤 | 流程顺序是业务语义，且有隐含的应用状态同步依赖 |
| 多步骤并行执行 | 单 GUI 线程 + UIA，必然互相踩踏 |

### 4.4 为什么这个方案在你的架构上是低风险的

现有 `_find_flow_control_impl` 本来就是「多阶段瀑布 + 每阶段命中即 return」的结构。插入一个"第 0 阶段：先试记忆路由"：

- **最坏情况** = 现状 + 一次 1.5 s 以内的廉价尝试；
- **不改变任何失败语义**——记忆路由 miss 后走的是与原样完全相同的链路；
- **可一键关闭**（配置项 / 编辑器面板），不需要改代码回滚。
