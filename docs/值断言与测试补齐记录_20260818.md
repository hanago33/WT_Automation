# 值断言(value_equals/nonempty)与测试补齐记录 2026-08-18

> 起因：流程里"假成功"会让错误一路滚到后面才暴露（如 step6-8 无断言标记 success，错误吞到 step9）。目标：给普通 action 步骤加"效果断言"——步骤动作后必须读到软件真实状态变化才算成功，当场拦截假成功，不再滞后。本次还补齐了既有 P0 改造遗留的 9 个断测，并做真机自测。代码改动对标 `docs/定位与MUP可靠性修复方案_20260817.md` 的 P0-4/P0-5。

## 1. 值断言功能（本次核心交付）

用户明确不要截图（不是多模态），只走结构化数据：UIA 值快照 + 断言 + 当场停。

### 1.1 新增 `value_equals` / `nonempty` 两个续跑条件

- **位置**：`wt_flow_locator.py` `wait_for_flow_control_condition`（原仅 exists/present/visible/enabled/gone）。
- **能力**：动作后读目标控件的实际值，`nonempty`=值非空，`value_equals`=值等于预期。比较前 `_normalize_compare_value` 去首尾空白、统一大小写（容输入框尾随换行/空格）。
- **读值**：复用现有 `get_wrapper_value`（ValuePattern → get_value → LegacyIAccessible 链），对下拉框会沿父级/子级 Edit 找值。

### 1.2 自动取动作值（零配置即生效）

- **位置**：`wt_flow_executor.py` `_resolve_continue_when`（新增第 2 参 `step_definition`）。
- **行为**：输入/选择类动作（type_text / type_text_relative / send_keys / set_text / set_combobox / select_dropdown_item_runtime / set_value 等）且未显式配 continueWhen 时，自动生成断言：
  - 从 actionConfig 取预期值，优先级 `inputText > value > text`；取到 → `value_equals`；取不到 → 降级 `nonempty`（仍能拦"空值假成功"）。
  - 显式配了 `value_equals`/`nonempty` 但没填 expectedValue → 同样从动作值自动回填；`value_equals` 取不到值 → 降级 `nonempty`。
  - controlId 从 `actionConfig.controlId`（或 controlRef）取；取不到则不生成（优雅跳过）。

### 1.3 断言失败当场停 + 结构化证据

- **当场停**：`_wait_for_continue_when` 断言不满足 → 抛 `RuntimeError` 走失败链路（与既有 visible/enabled 等一致），不让错误滚到下一个卡住步骤。
- **证据落盘**：新增 `_write_failed_continue_when_evidence`，失败时把条件、预期值、目标控件 UIA 值快照写入 `logs/evidence/step_<id>.json`（结构化 JSON，可事后定位根因，不靠截图）。
- **接线**：`configure_flow_executor` 新增 `find_flow_control`、`get_wrapper_value_snapshot` 两个注入点；`WT_AUT_recorded.py` 用 `wt_flow_locator` 的属性接好。

### 1.4 测试

- 新增 `tests/test_wt_flow_executor_value_assert.py`（13 用例）：覆盖自动取值、显式值条件降级、nonempty/value_equals 匹配/不匹配/空值/首尾空白容错、控件缺失。

## 3. 真机自测（记事本）+ 下拉实测的诚实结论

按既有自测纪律（先自测优化再交付），对值断言做了真实目标实测。

### 3.1 记事本实测 PASS（临时脚本已删）

- **关键发现**：Windows 11 新版记事本编辑区是 `RichEditD2DPT`（UIA `Document` 类型），**不是经典 `Edit` 控件**——这在 mock 里永远发现不了。
- `get_wrapper_value` 在真实 UIA 控件上可靠：键入 `CFT01test` 后读回 `'CFT01test'`，读值耗时 ~9ms。
- 四个断言分支全部真机验证：nonempty（有值→True）、value_equals（匹配→True / 不匹配→False）、清空后 nonempty（→False，拦空值）。
- 键入 215ms、读值 9ms → 断言开销极小。

### 3.2 下拉（Word/原生 ComboBox）实测的结论

试了几条路都证明**收益低**，决定打住：

- **Word**：Ribbon 用 Office 自定义控件类型，UIA 下不是标准 `ComboBox`，找不到可断言下拉；
- **Win11 记事本"另存为"对话框**：WinUI/XAML 控件，同样不是标准 ComboBox；
- **自建 Win32 COMBOBOX 宿主**：Python 3.8 `ctypes.wintypes` 缺 `WNDCLASSW`/`LRESULT`，平台工程成本极高，且即便造出来测的还是**同一条 ValuePattern 路径**，无新增信息。

**核心判断**：`get_wrapper_value` 读控件值走 `_read_wrapper_value_raw`（ValuePattern→get_value→LegacyIAccessible），这个读值机制**已被记事本实测证明在真实 UIA 控件上可靠**。下拉框选中项走的正是同一路径。**唯一替代品模拟不了的是 Telerik RadComboBox 的专属暴露**（ValuePattern 在父级、可编辑下拉当前文本在子级 PART_EditableTextBox）——只能等 MUP 运行时在真实粗糙度/投影下拉上验证。

## 5. 后续真机自测结论（2026-08-18 追加）

按用户建议对 `menu_select_flow` 与"焦点落位"做了记事本实测，结论如下（均在 Win11 新版记事本上）。

### 5.1 `menu_select_flow` 记事本测不了（兼容盲区）

**现象**：Win11 新版记事本**没有 Win32 菜单**（`UIAWrapper.menu()` 不存在，菜单是 UIA `MenuBar`）。`menu_select_flow`（`wt_flow_locator.py:2598`）走 `dlg.menu_select(menu_path)`（Win32 菜单 API）→ **对 Win11 记事本无效**。与下拉同理：需带传统 Win32 菜单的真实目标或 MUP 本身才能验证。该函数当前 **0 个测试文件覆盖**，是最缺保护的一处。

### 5.2 焦点落位主链路真机正常，但发现假阴性隐患

**真机验证通过**：
- `_get_focused_element()` 能正确取到焦点元素（记事本编辑区 → `Document`）
- `_focus_lands_on_anchor(doc)` 返回 `True`（`wt_flow_locator.py:1073` 判定成立）

**发现的隐患**：`get_wrapper_has_keyboard_focus`（`wt_flow_locator.py:609`，读 `element_info.has_keyboard_focus`）对 Win11 记事本 `RichEditD2DPT`（Document 控件）返回**假阴性 `False`**——即便控件实际有焦点且能键入（键入 `abc` 后 `get_wrapper_value` 读回成功）。

**影响面（均非必然 bug，条件触发）**：
1. `get_wrapper_debug_snapshot` / descendant 摘要（`wt_flow_locator.py:1376,1431`）——仅快照字段显示不准；
2. **`auxChecks` 的 `HasKeyboardFocus` 校验**（`wt_flow_locator.py:2931`）——若流程步骤把 `HasKeyboardFocus` 配成判定条件，对这类真实控件（WinUI Document、可能含部分 Telerik 控件）会**误判失败**；
3. 采集器 `build_control_map_library.py` / 编辑器 `WT_Flow_Editor.py` 的 inspect 展示字段。

**处置**：暂不修复（影响面小、仅 auxChecks + 快照展示；改它涉及 Win32 `GetGUIThreadInfo`/`GetFocus` 兜底，需谨慎评估对采集器的影响）。若未来确认流程会配 `auxChecks.HasKeyboardFocus` 再处理。
