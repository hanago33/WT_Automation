# 卷二 · 录制数据模型与事件聚合（legacy 精读）

> 依据：`legacy/openadapt/models.py`（1,217 行）、`legacy/openadapt/events.py`（982 行）、`legacy/openadapt/cache.py`、`legacy/openadapt/strategies/base.py`。
> legacy 已冻结但数据模型思想延续到新 capture 包；本卷聚焦**录制产物该怎么建模**。

## 1. Recording：一次演示会话的容器（models.py:46-127）

```python
class Recording(db.Base):
    timestamp, monitor_width, monitor_height,
    double_click_interval_seconds, double_click_distance_pixels,   # 平台双击参数随录制固化！
    platform, task_description, video_start_time, config(JSON)
    action_events / screenshots / window_events / browser_events / audio_info   # 五类事件流，按时间序
    original_recording_id   # 录制的"副本血缘"（脱敏副本指向原件）
```

两个易忽视的设计：

- **平台参数随录制存档**：`double_click_interval_seconds/distance_pixels` 是录制机器的系统值——回放端用它复现"当时算不算双击"，而不是依赖回放机器的设置。WT 的录制转换器目前不存这类采集环境参数。
- **副本血缘**：`original_recording_id` 自引用，`scrubbed_recordings` 关系——脱敏副本与原件并存且可追溯，而不是覆盖。

## 2. ActionEvent：动作事件 schema（models.py:129-234）

| 字段组 | 字段 | 设计要点 |
|---|---|---|
| 五元组引用 | `timestamp` + `recording/screenshot/window_event/browser_event` 各自的 `_timestamp` + `_id` **双引用** | 每个动作同时携带"当时的屏幕帧、当时的活动窗口、当时的浏览器态"——**动作上下文是一等公民**，回放/检索/报告都靠它 |
| 鼠标 | `mouse_x/y` + `mouse_dx/dy`（增量） | 拖拽/滚轮可重建轨迹 |
| 键盘 | `key_name/key_char/key_vk` + **canonical 三态副本** | canonical 化（跨平台键名归一：darwin 的 `<esc>`==`<53>`）使回放与比较不依赖原始平台；**原始与规范双存**，审计可回看原始 |
| 聚合层级 | `parent_id` + `children` + `reducer_names`(set) | 聚合后的复合事件保留原始子事件（type 事件下挂逐次 press）；**记录用了哪些归并规则**——可解释的降抽象 |
| UI 结构 | `element_state`(JSON) + `active_segment_description` / `available_segment_descriptions` | a11y/分割证据随事件存档；segment 描述用于视觉定位候选 |
| 隐私 | `scrubbed_text` / `scrubbed_canonical_text` | 脱敏发生在数据模型层（读取 text 属性时优先返回脱敏值，models.py:313-318），不是外挂后处理 |
| 生命周期 | `disabled`(bool) | 事件可禁用不可删——编辑历史可审计 |

**对照 WT**：`WT_AUT_recorded.py`/`flow_recorder_converter.py` 的步骤 JSON 有控件引用+参数，但**没有**"动作前的屏幕帧引用、当时的窗口态、归并规则痕迹"三件事。卷五建议：录制转换产物增加 `screenshot_ref`（动作前帧，已有 recorder_captures 基础）与 `window_title_at_action` 字段——排障时"当时在哪个窗口点的这个控件"从此有据可查。

## 3. 事件聚合管线：Literal → Symbolic 的 8 步（events.py）

```
merge_events 总入口，按序：
1. filter_invalid_window_events     剔除非法窗口事件
2. merge_consecutive_mouse_move_events     连续移动合并
3. remove_redundant_mouse_move_events      去冗余移动
4. merge_consecutive_mouse_scroll_events   连续滚动合并
5. remove_move_before_click               点前移动剔除（点击语义归点击）
6. merge_consecutive_mouse_click_events   连点→双击/三击
7. remove_invalid_keyboard_events         非法键盘事件剔除
8. merge_consecutive_keyboard_events      连键→type 事件
9. merge_consecutive_action_events        跨类型相邻动作合并（make_parent_event 挂父子）
10. discard_unused_events                 未引用事件丢弃
```

要点：①**归并规则是显式管线**（每步一个纯函数，可单测可回溯），不是黑盒推断；②`make_parent_event` 把聚合产物挂为父事件、原始事件为 children——**降抽象不丢信息**；③双击判定用 Recording 里存档的平台参数（§1）。

**对照 WT**：`flow_recorder_converter.py` 的 recorder 语义转换做了类似的"原始→步骤"翻译，但归并规则内嵌于转换主流程。可借鉴点：把"连点→双击、连键→输入、移动剔除"拆成显式的有序管线函数列表，每步可独立测试、可按需增删——WT 的录制转换规则会持续增长，管线化是防复杂度失控的结构。

## 4. 缓存（cache.py，157 行）——编译/推理成本控制的朴素形态

`@cache()` 装饰器基于 `joblib.Memory` 落盘函数级缓存（含 `check_call_in_cache` 预检、`force_refresh`、按天清理 CLI）。用于 LLM 适配器调用的幂等缓存。对照 Skyvern 的代码缓存：joblib 缓存是"同一输入同一输出"的函数级记忆，**不生成可审查的程序**——这正是 OpenAdapt 后来转向"演示编译为确定性程序"的原因（函数缓存仍依赖模型在环）。WT 的 Agent（知识库/flow repair 已有 history_store）若要做 LLM 结果缓存，joblib 方案一天可落地，但**终态应是 Skyvern/OpenAdapt 式的"编译产物缓存"**。

## 5. 回放循环与"动作完成判定"（strategies/base.py）

- `run()` 主循环（:56-115）：截图→窗口事件→策略决策→播放→**FPS 自监控**（frame_times 滑窗均值，:117-127）——回放节奏本身是可观测指标；
- 时间戳单调断言（:85-95）：上一个动作时间戳必须 ≤ 当前——事件流乱序直接告警；
- `prompt_is_action_complete`（:140-176）：LLM 判断"刚执行的动作是否完成"，输出 `{expected_state, is_complete}` 结构——**期望状态显式化**的思想后来进化为 flow 的 Postcondition/Effect 契约（卷三）；alpha 时代因成本默认关闭（`CHECK_ACTION_COMPLETE=False`），现代架构用"编译期确定契约 + 运行时确定性核查"替代了"运行时问模型"——**这个替代本身是最重要的教训**：能编译成断言的，不要留给模型现场判断。
