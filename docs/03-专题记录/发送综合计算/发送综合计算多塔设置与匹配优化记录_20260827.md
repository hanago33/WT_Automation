## 二、需求决策（用户确认）

1. 三个"临时壳"步骤 → **替换为真实控件并修正**。
2. 多塔时极风参考点 → **选参考点测风塔**（`${stepParams.refmast}`），非 mettowername/M1。
3. 气象参考环节 → **单塔执行 step_13-15（标 `towerTags=["single"]`），多塔走多塔组**，互斥。
4. **只建立 4 个综合，综合名保持综合1-4**；单塔/多塔由项目条件自动决定：
   - 项目文件夹解析到 **1 个测风塔** → 综合1-4 全单塔；
   - 解析到 **≥2 个测风塔** → 综合1-4 全多塔。
5. 综合描述（原写死 `Test1`）→ 改为注入 **机型 + 单/多塔**（如 `WT6250D220 多塔`）。

### 3.2 `WT_AUTOMATION_Agent/parameter_scan.py`

`ParameterScanner.scan` 新增可选参数 **`tower_mode_override: str | None`**：
- 非 None（`"single"`/`"multi"`）时，读表后强制把每行 `values["towermode"]` 覆盖为同值，
  **不改参数表文件**（纯内存）。
- 非法值打印警告并忽略覆盖；默认 None 保持原行为，向后兼容。

### 3.3 `WT_AUT_recorded.py`

1. **新增 `_load_json_env_runtime()`**（约 726 行）：读 `GM_RUNTIME_CONFIG_JSON`
   环境变量（Simple 界面注入的项目解析结果），返回 dict，失败返回 {}。
2. **`_apply_param_table_expansion` 单塔/多塔自动决定**（约 746-774 行）：
   - 从流程 runtimeConfig / env runtime 读 `mastIds` 与显式 `towerMode`；
   - 显式 `towerMode` 优先，否则 `mastIds` 长度 ≥2 → `"multi"`；
   - 计算结果传给 `ParameterScanner.scan(tower_mode_override=...)`。
3. **`_load_runtime_config` 透传扩展键**（约 839-863 行）：在 6 个固定键
   （gmExe/sourceFilePath/outputDir/projectionFilePath/controlMapPath/templateAutoUpdate）
   之外，**合并 env_runtime + flow_runtime 的全部额外键**（mastIds/turbineType/
   synthesisDesc/towerMode 等），供 `${runtime.xxx}` 占位替换与运行期逻辑使用。
4. **包 stepIds 映射修复（bug）**（约 810-838 行）：展开后把包 `stepIds` 从模板 id
   映射为 `_scan` 展开 id 时，**被行级过滤排除的步骤 id 直接丢弃**，不再原样保留。
   原逻辑 `elif pid: new_step_ids.append(pid)` 在多塔模式下会残留
   `step_13/14/15/18/24a` 等被过滤的单塔步骤 → `validate_flow_definition` 报
   "流程包引用了不存在的步骤"。

### 3.4 `WT_Launcher.py`（Simple 界面）

`_launch_automation` 项目注入分支（约 4613-4637 行）：
- 用 `wt_project_workdir_parser.list_mast_entries(project_work_dir)` 获取测风塔列表，
  `mastIds` 数量 ≥2 → `towerMode="multi"`，否则 `"single"`（仅解析到塔时才注入）；
- 拼 `synthesisDesc = "{turbineType} {多塔|单塔}"`（turbineType 缺省时仅塔模式）；
- 二者写入 `runtime_config`，经 `GM_RUNTIME_CONFIG_JSON` 传给子进程；
- 日志输出 `项目条件：测风塔 N 座 → 多塔/单塔，综合描述=...`。

### 3.5 数据流（一次运行）

```
Simple 界面选项目文件夹
  └─ wt_project_workdir_parser.parse_project_work_dir
       ├─ list_mast_entries(CFT信息.txt) → mastIds 数量
       └─ runtime_config += { towerMode, synthesisDesc }
            │  GM_RUNTIME_CONFIG_JSON 环境变量
            ▼
WT_AUT_recorded._apply_param_table_expansion
  ├─ 读 env runtime：mastIds≥2 → tower_mode_override="multi"
  └─ ParameterScanner.scan(tower_mode_override=...)
       └─ 参数表每行 towermode 覆盖 → 双维过滤展开
            ├─ multi → 96 步（含 step_mt 组 16 步，排除 step_13/14/15/18/24a）
            └─ single → 90 步（原行为）
执行期 _resolve_dynamic_value 替换：
  ${runtime.synthesisDesc} → "WT6250D220 多塔"（step_4 描述）
  ${stepParams.refmast}    → 参考点测风塔（step_mt_refpoint / step_mt_extreme_ref）
  ${stepParams.refclimatology} → 参考气象名（step_mt_refclim_search/select）
```

## 五、实测前注意事项（后续实测后再回来优化）

1. **`step_mt_extreme_ref` 控件可用性待实跑确认**：多塔界面下极风速"在测风对象"下拉
   （`PART_DropDownButton,Button,在测风对象`）是否存在未 100% 确认（控件库未扫到
   多塔专用变体）。若未命中：

   - 备用 B：确认多塔界面无此下拉时，降级为可选步骤并更新 notes。
2. **多塔"气象"弹窗复用**：`step_mt_refclim_search/select` 用的
   `MTDClimatologySelectorControl` 与单塔共用，但多塔下弹窗可能是模态叠加层；
   若命中失败检查运行时弹窗内是否出现第二个"全文检索"（ui_path 已限定容器）。
3. **`step_mt_add`（添加塔）默认 `enabled:false`**：两座塔无需添加；**三座及以上塔
   需手动改为 true**。后续可考虑按测风塔数量自动启用。
4. **CFT信息.txt 编码**：UTF-8（表头 `# mastName lon lat elev hubHeight utmX utmY`）。
   `_parse_cft_info_file` 用 `utf-8, errors="ignore"` 读取，乱码风险低；但 read_file
   工具直接读会显示乱码（工具编码探测问题，文件本身正常）。
5. **不要用 Launcher 流程编辑器保存** `flow_definition_发送综合计算.json`——
   会剥离 `stepTags`/`towerTags`，导致双维过滤失效（沿用 20260824 记录的重要提醒）。
6. **多次运行前建议清空综合列表**，避免副本继续往后编号（综合5/6/7）。
7. `workspace/flow_definition.json` 是默认流程（气象数据录入），真实运行发送综合计算
   时 Simple 界面会设 `WT_FLOW_DEFINITION_FILE` 指向 flow_packages 下的流程文件；
   直接调 `WT_AUT_recorded` 调试时需手动设该环境变量。
