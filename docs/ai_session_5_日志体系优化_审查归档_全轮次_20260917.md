## 二、必须知道的 7 个环境坑（实施会话已验证 + 审查者复核）

> 这些坑会让 AI 白白浪费时间，且**其中 3 个会让 AI 误判「代码有 bug」**。

### 坑 1：本机 git 无法写入嵌套 ref（严重）

`git branch ai/x` / `git update-ref refs/heads/ai/x` / `git worktree add -b ai/x`
**均静默失败**（退出码 0，reflog 写了但 ref 文件不落盘，回滚还会删掉整个 `.git/refs/heads/ai/` 目录）。

**后果**：worktree HEAD 变成 unborn，`git status` 会把**全仓文件误报为新增**（`A`），
提交会产出 root commit。

**绕过**：手工写 ref 文件，或用非嵌套 tag 作锚点：
```bash
mkdir -p .git/refs/heads/ai && printf '<40位hash>\n' > .git/refs/heads/ai/session-N
git tag -f ai-session-N-backup      # 非嵌套 tag，可靠
```
**每次 commit 后必须复查 HEAD。**

### 坑 2：沙箱禁止写入 `ai5`（会让 AI 误判代码有 bug）

审查者的沙箱（workspace-write，workspace = `D:\My_RF_Project\WT_Automation`）**拒绝写入 `ai5`**。
在 `ai5` 内直接跑 pytest 会产生：

- `JsonlSidecarTests` **12 项失败**
- `log_step` 在 `wt_run_status.publish()` 的 `NamedTemporaryFile`（`wt_run_status.py:86`）处**自旋/挂死**

**这两者都是沙箱禁写所致，不是代码缺陷。** 用 `faulthandler` 定位到自旋点后确认。

**绕过**：复制到可写目录再跑（审查者用的方法，见坑 3）。

### 3.2 🔴 P0-2：运行收尾两行恒被判 ERROR（假红字）★ 最高优先级

**位置**：
- `WT_AUT_recorded.py:571` `def _log_run_end_banner(run_report, status)`（调用点 L2806 / L2834）
- `wt_run_reporting.py:154` 附近（运行结果摘要行）

**根因链**：
1. 两处都是 `log_step(单参数)` 调用，级别靠 `wt_logging.detect_level()` **猜文本**
2. banner 的 `extra` 恒含「失败 0」——因为 `wt_run_reporting.py:67` 把 `failedCount` **初始化为 0**，
   成功运行也一定有这个字段
3. 摘要行恒含 `failed=0`
4. 而 `wt_logging._BENIGN_ERROR_CONTEXT`（L403）**不含** `失败 0` / `failed=0` 这两个模式
5. → `detect_level()` 看到「失败」二字即判 ERROR

**端到端复现（决定性证据）**：审查者调用**真实的** `WT_AUT_recorded._log_run_end_banner()`，
传入符合 `wt_run_reporting.start_run_report()` 结构的成功报告（`failedCount: 0`），
捕获它**实际写出的日志行**：

```
[2026-09-17 11:37:26.129] [ERROR] ========== 运行结束 · 状态=成功 · 用时 123.4s · 步骤 16 步 · 成功 16 / 失败 0 ==========
[2026-09-17 11:37:26.129] [ERROR] ========== 运行结束 · 状态=失败 · 用时 9.9s · 步骤 16 步 · 成功 1 / 失败 15 ==========
```

**成功与失败完全同级（均为 ERROR）**。`[ERROR]` 是 `format_line()` 写入时定下的级别 token，
即**线上日志文件里真实会出现这两行红字**。

#### 🔺 影响升级：P0-2 已扩散到 `wt_log_query`（`464c621`）

`wt_log_query.level_of()`（L51-57）对**无显式级别 token 的行**回退到 `wt_logging.detect_level()`
——正是 P0-2 的根因函数：

```python
def level_of(line):
    """取一行的级别：优先读显式 token，历史行回退关键字推断。"""
    text = str(line or "")
    explicit = wt_logging.level_from_line(text)
    if explicit is not None:
        return explicit
    return wt_logging.detect_level(text)      # ← P0-2 根因函数
```

实测（用代码中**真实消息模板**构造的 3 步成功运行日志）：

| 场景 | 结果 |
|---|---|
| 新格式日志（成功运行） | 摘要 `共 3 行 · ERROR 1 · INFO 2` ← **成功运行被统计出 ERROR** |
| 老格式日志（成功运行） | 同样 `ERROR 1` |
| **用户选「ERROR 及以上」过滤** | **只返回那行「运行结束 · 状态=成功」** |

**这让 P0-2 从「视觉噪音」升级为「功能性误导」**：`wt_log_query` 与 P3 过滤条的设计目的
正是「定位第一个出问题的步骤」（见 `464c621` / `6b0346c` 提交信息），
而用户筛 ERROR 得到的却是运行成功的那行。

#### 测试盲区（重要）

`tests/test_log_query.py` 有一个 `test_historical_success_line`，**名字看似已覆盖此场景**，
但它用的输入是一行**普通步骤日志**（`已通过流程链路匹配点击控件`），**不是真实的运行收尾行**：

| 输入 | `level_of()` |

即：该测试**恰好绕开了 P0-2**。33 项测试全绿，但覆盖不到这个真实场景。

**修复建议**：
1. 两处显式传级别（`_log_run_end_banner` 里按 `status` 传 `SUCCESS`/`ERROR`；
   摘要行按实际结果传）
2. 把 `失败 0`、`failed=0` 补入 `_BENIGN_ERROR_CONTEXT`
3. **补一条用真实 banner 文本的测试**（照抄 §3.2 的实测字符串）

**后果**：`6c4d696` 的核心设计声明是
「文本日志为人读而精简，JSONL 为机读而完整……**『精简文本』与『保留全量调试数据』不再互相冲突**」。
**实测该目标未达成**：被降噪砍掉的诊断数据（`[定位耗时]` 分段计时、`[DEBUG] click_flow_control 判定`、
剪枝计数）在**任何开关状态下都不进 JSONL** —— 除非开 DEBUG 档，但那时文本日志也全都有了，
JSONL 不再提供增量价值。**当前 JSONL 只是文本日志的重复副本。**

**修复建议**：把 `log_event()` 移到门控 `return` **之前**（文本受门控、JSONL 不受）：
```python
    if resolved is None:
        resolved = wt_logging.detect_level(step_name)
    # JSONL 旁路不受级别门控：机读数据要全量，人读文本才精简
    wt_logging.log_event(resolved, step_name)
    if not wt_logging.is_enabled(resolved):
        return
    _append_log_file(...)
```

### 4.1 专章：日志面板永久冻结（跨会话交叉验证）

**此问题由另一并发会话（session-6）的 UI 审计报告提出，本审查独立复现确认。**

**缺陷机制**：
```python
else:
    current = rendered_count()
    if len(text_lines) > current:        # ← 等长位移时恒为假
        for line in text_lines[current:]:
            widget.insert(tk.END, line + "\n", self._classify_line(line))
```
两个成因叠加：
1. `len(text_lines) > current` 在**等长位移**时恒假（服务端 tail=300，窗口滑动但长度不变）
2. `_LOG_MAX_LINES = 400` **大于**服务端 `DEFAULT_TAIL = 300`，**trim 永不触发**

**作者的注释自证了意图与缺陷的矛盾**（`wt_task_queue_window.py:1888-1890`）：
```python
# 日志面板增量渲染参数：行数上限（超过从头 trim），与服务器 /api/logs?tail 的
# 300 行对齐再留余量；_render_*_logs 在轮询间只 append 新行，不再每 2s 全量
# delete+insert（全量重绘会让日志区在用户拖动/选择时闪一整帧）。
_LOG_MAX_LINES = 400
```
本意是「300 行对齐再留余量」（400 = 300 + 100），**但 400 > 300 恰恰使 trim 永不触发**
——正是冻结的成因。作者写这段注释时，把「留余量」和「能触发 trim」两个目标搞反了。

**真实 `tk.Text` 控件复现（决定性证据）**：审查者直接调用**真实的**
`TaskQueueWindow._append_lines_incremental()`（未复制逻辑，仅借壳调用）：

| 轮次 | 服务端行数 | 控件显示行数 | 控件末行 |
|---|---|---|---|
| 1 | 300 | 300 | `第 299 行` |
| 2 | 301 | 300 | `第 299 行` ← **卡住** |
| 3 | 302 | 300 | `第 299 行` |
| 4 | 303 | 300 | `第 299 行` |
| 5 | 304 | 300 | `第 299 行` |
| 6 | **305** | 300 | **`第 299 行`** |

最终：服务端真实最新行 = `第 304 行`，**控件实际显示末行 = `第 299 行`**。
面板从第 2 轮起不再更新，此后**永久冻结**。

**影响面与逃生口**：

| 面板 | 数据源 | 冻结后能否恢复 |
|---|---|---|
| `monitor_log_text`（**运行日志** 页签，默认自动轮询开启） | `/api/logs?tail=300` | ❌ **无任何逃生口** —— `_clear_log_text`（L1738）只清 `log_text`，全仓**没有**任何地方重置 `_monitor_log_rendered_lines` |
| `log_text`（终端控制台） | `/api/tasks/<id>/logs?tail=300` | ⚠️ 可点「清屏」按钮（L672 → `_clear_log_text`）重置 `_log_rendered_lines = 0`，使下一轮轮询走全量重绘而暂时恢复 |

**严重度**：运行日志页签是用户远程监控运行进度的主界面。主日志为追加式，每步写数行，
累计 300 行约对应 50~75 步 —— **111 步的长流程必然触发，且触发后无法恢复**（除非关闭重开窗口）。

**与本次改动的关系**：
- 该缺陷在 `main` 上**已存在**，不是 session-5 引入
- 但本次改动与之有**两处耦合**：
  1. `WT_AUT_recorded.py:322` **新增**了 `MonitorWindow.LOG_MAX_LINES = 400`，把同一问题常量复制到新模块
  2. `tests/test_log_lifecycle.py` 新增 `test_cap_matches_queue_window_for_consistency`，
     **断言两处 400 必须相等**

**关于该断言的精确影响**（此处修正初稿措辞）：它**不构成修复阻碍** —— 把两处上限**同步**降到
`<= 300` 时等式仍成立，测试照样通过。它的实际作用是**强制两处常量同步变更**：只改一处会失败。
考虑到现在共有 3 个地方引用该数值（`wt_task_queue_window._LOG_MAX_LINES`、
`WT_AUT_recorded.MonitorWindow.LOG_MAX_LINES`、该断言），修复时需一并调整。

**修复建议**：上限应取 `<= SERVER_TAIL(300)`；更稳妥的做法是让控件上限**由服务端 tail 派生**
（而非各自硬编码），从根上消除这类不一致。

**⚠️ 注意 `WT_Launcher` 的两个面板不受此缺陷影响**（易混淆，此处澄清）：

| 面板 | 类 / 位置 | 数据源 | 渲染方式 | 受冻结影响 |
|---|---|---|---|---|
| 总控台「运行日志」页 | `LauncherApp`（`log_text` L5395） | **本地文件** `LOG_FILE` | P3 新增缓冲 + 增量插入 | ❌ 不受影响 |
| 服务器监视窗 | `ServerMonitorWindow`（`log_text` L1704） | `/api/logs?tail=300` | **`_render_logs` 每轮全量 `delete`+`insert` 重绘** | ❌ 不受影响 |

两个 `self.log_text` 分属**不同类**，无命名冲突。
**即：冻结缺陷只在 `wt_task_queue_window` 中存在**，P3 只改了总控台，队列窗口仍未修。
