## 一、背景：服务器部署 + 会话重启 + 远程验证的标准操作清单

一次"新包上服务器并验证远程执行"的标准流程（原人工版本 7 步）：

1. 部署发布包 zip，覆盖到服务器 `D:\My_RF_Project\WT_Automation\`
2. 跑 `diagnose_session.py`：核对 `MUPSmartClient.exe` 与 `wt_task_server`/`wt_queue_selfcheck`
   的 SessionId 一致（都应是当前 PowerShell 的 session，通常 1）
3. 若服务不在当前 session → `Stop-Process` 杀净旧服务
4. 当前会话重启：`start_queue_service.bat`（窗口保持打开）
5. 重新提交远程任务 → 健康检查应看到 `size=1920x1040`（而非 160×28 小窗）
6. GM_EXE 配置从桌面 `.lnk` 改为 `C:\Program Files\Meteodyn\MeteodynUniverse\MUPSmartClient.exe`
7. 若步骤报「未命中控件」→ 检查权限一致性（MUP 管理员 ↔ 服务普通权限，UIPI 问题）

其中步骤 2~4 的"诊断→杀→重启"是人工串联的，且旧版 `wt_queue_selfcheck.py --server`
的 `ensure_service` 只在**端口未监听**时才启动——旧服务还活着时不杀、不重启，
这正是流程里必须手动 `Stop-Process` 的原因。

## 二、本次排障主线索：任务"没到服务器"

### 2.1 现象
按流程部署 + 重启服务 + 提交远程任务后：
- 服务器端"没有任何动静"
- 本地机（内网本地机）的 MUP 被唤醒/被操作，且停留在「导入时间序列文件」界面
- 服务器任务日志显示任务**确实启动了**（`[queue] starting task task_...`），但
  所有步骤 `action click 未命中控件`（窗口枚举只有 `导入时间序列文件` dialog 和一个空 title 窗口）

### 2.2 证据链（排查过程）
- 本地机（工作区机器）上检查：无 `wt_task_server` 进程、8768/8767 无监听、
  `logs\tasks\` 下**没有** `task_20260902_110225_89ce12.log`、`task_queue.db` 无该任务记录
  → 任务日志不在这台机器。
- 但任务日志确实存在且完整 → 说明任务被**另一台机器上的 wt_task_server** 接收并执行了。
- 服务器 `wt_queue_selfcheck.py --server` 输出：`服务器地址：http://10.102.96.63:8768/`，
  服务健康 `wt_task_server`，令牌 `wt2026`。

### 2.3 根因（决定性）
用户总控台「任务服务地址」填的是 **`http://127.0.0.1:8768`**，且总控台运行在
**内网本地机**上 → `127.0.0.1` 指向**本地机自己** → 任务提交给了本地机上跑的
`wt_task_server` → worker 操作的是**本地机的 MUP**（停在导入界面）→ 主窗口步骤全部未命中。
服务器全程未收到任何请求。

> **核心教训（Lesson）**：`127.0.0.1` 是"运行总控台的那台机器自己"，不是"服务器"。
> 判断"任务是否真到服务器"，只看**服务器**的 `logs\tasks\` 有没有生成新日志，
> 不能看总控台/本地机表现。

### 2.4 伴随问题：取消/删除按钮报错
- 取消 → `409 cancel is only valid for pending tasks`：任务已 running，API 拒绝 cancel；
  **UI 应在 running 时把取消按钮置灰**（当前未做，属 UI bug）。
- 删除 → `404 not found`：DELETE 路由/`taskId` 参数未匹配，需查 `wt_task_server.py` 路由。

### 2.5 正确的填写方式（按总控台所在机器区分）
| 场景 | 任务服务地址 | 令牌 | 用户名 |
|---|---|---|---|
| **在服务器上**打开总控台 | `http://127.0.0.1:8768`（本机即服务） | `wt2026` | 任意（如 LiaoJP） |
| **在内网本地机**打开总控台 | `http://10.102.96.63:8768`（服务器 IP） | `wt2026` | 任意 |

注意：填服务器 IP 前需确认本地机→服务器网络通 + 防火墙放行 8768/8767 入站：
```
netsh advfirewall firewall add rule name="WT_Queue_8768" dir=in action=allow protocol=TCP localport=8768
netsh advfirewall firewall add rule name="WT_Monitor_8767" dir=in action=allow protocol=TCP localport=8767
```
`10.102.96.63` 这类 IP 是给"其他机器连服务器"用的；服务器本机用 `127.0.0.1` 最稳，绕过防火墙。

## 三、流程简化落地（本会话产出）

把原 7 步人工流程压缩为 **1 条命令 + 1 次验证**，并补齐诊断能力。

### 3.1 `wt_queue_selfcheck.py` 新增 `--force`（幂等重启）
```powershell
D:\wt_python\python.exe wt_queue_selfcheck.py --server --force
```
= 一步完成「杀净 8768/8767 旧服务 → 当前会话重启 → 健康自检」，替代原步骤 3+4。
（旧版在端口已监听时会跳过启动——`--force` 先 `cmd_stop()` 再 `cmd_server()`。）

> 坑：新增参数只改本地工作区，**不重打发布包就不会到服务器** —— 本次即因服务器
> 跑旧版报 `unrecognized arguments: --force`。发布包由 `make_release.py` 生成，
> 需重新生成并部署（或直接覆盖单文件修复包）。

### 3.2 `diagnose_session.py` 增强：UIPI 权限一致性检查
诊断输出新增：
- `[MISMATCH]` 行：MUP / 队列服务不在当前 session 时直接标出；
- `== UIPI 权限一致性检查 ==`：查询 `MUPSmartClient.exe` 与队列服务的提权状态，
  若 MUP 管理员 + 服务普通权限 → 提示 UIPI 风险（步骤报「未命中控件」的候选根因之一）；
  若无服务在跑则跳过判定（避免误报）。

### 3.3 新增 `fix_server_gm_exe.py`
一键把 `resources/project_config.resource` 的 `${GM_EXE}` 从 `.lnk` 改为
`C:\Program Files\Meteodyn\MeteodynUniverse\MUPSmartClient.exe`（幂等）。
注意：resource 为 RobotFramework 格式，反斜杠需双写 `\\`；服务端解析时
`value.replace("\\\\", "\\")` 会还原为单反斜杠，二者已实测兼容。

### 3.4 新增 `服务器一键会话修复.bat`
```
用法1：服务器一键会话修复.bat                     # 只修服务
用法2：服务器一键会话修复.bat 发布包_xxx.zip       # 先部署再修服务
```
依次执行：部署发布包（可选）→ 会话诊断（SessionId+UIPI）→ `--server --force` 重启 →
GM_EXE 修复 → 打印下一步验证指引。已加 `chcp 65001 >nul`（GBK 控制台显示 UTF-8 中文）。

### 3.5 发布流程配套
- `make_release.py`（增量发布包）会包含工作区未提交/未跟踪的改动；改完运维脚本后
  需重新 `python make_release.py` 生成新包再部署。
- 临时小修复包可手动 zip 指定文件（`wt_queue_selfcheck.py` / `diagnose_session.py` /
  `fix_server_gm_exe.py` / `服务器一键会话修复.bat` / `resources/project_config.resource`）。

## 四、运维事故教训（误删发布包）

清理"GBK 乱码 zip"时，删除条件 `"_20260902" in name` 写得太宽，误删了 4 个正常发布包：
- `发布包_业务改动_20260902_103001_9ea7726.zip`：同名解压目录仍在 → 可重新打包恢复
- 3 个 `发布包_服务器联通测试完整_20260902_*.zip`：内网已有副本，可回传

> **Lesson（删除操作纪律）**：涉及删除时必须**先精确枚举目标清单**、逐一核对后再执行，
> 不要用"宽松包含匹配"批量删；误删后先查 同名解压目录 / git 跟踪 / 内网副本 / 回收站 四路恢复。

## 五、规则与自查清单（沉淀为工程纪律）

1. **"任务没到服务器" 三步定位**：
   ① 服务器 `logs\tasks\` 是否生成新任务日志（唯一权威证据）；
   ② 总控台地址是 `127.0.0.1` 还是服务器 IP（`127.0.0.1` = 运行总控台的机器自己）；
   ③ 本地机→服务器 TCP 8768 连通 + 防火墙放行。
2. **令牌一致性**：总控台 token 必须等于服务启动 `--auth-token`（本次本地存 `123`，
   服务器是 `wt2026`，改地址后必 401）。
3. **GM_EXE 直连 .exe**，避免 .lnk（换机/路径变化时不可靠）。
4. **`--server --force` 代替手工 Stop-Process**；先部署新包再覆盖修复文件，顺序勿反
   （旧包会覆盖新脚本为旧版）。
5. **删除文件前先列出精确清单**。
6. UI 上：任务 running 时「取消」按钮应置灰（避免 409 报错），属待修 UI 缺陷。
