# 卷一 · 项目全景与架构演进

> 依据：主仓库 `docs/architecture-evolution.md`（v3.0, 2026-01）、`docs/architecture.md`（canonical）、`source-policy.public.json`。

## 1. 项目身份

| 项 | 事实 |
|---|---|
| 名称 | OpenAdapt（OpenAdaptAI 组织，26 个公共仓库） |
| 许可 | 全线 MIT（源码级；OpenAdapt Cloud 控制面私有） |
| 定位 | **"受治理的演示编译器"（governed demonstration compiler）**：人演示任务 → 保留证据 → 编译确定性程序 → 按策略资格认证 → fail-closed 运行时执行 → **独立效果验证器**裁决 |
| 核心理念 | **演示条件化自动化（demo-conditioned）："show, don't tell"**——不是提示词驱动，而是演示驱动；官方数据：首动作准确率 提示词 ~33% vs 演示条件 ~100%（architecture-evolution.md §3） |
| 域 | 桌面（Windows/macOS/Linux）+ 浏览器（Playwright）+ 远程像素面（RDP/Citrix） |

**成熟度重评（修正此前判断）**：本系列影刃/竞品调研早期将 OpenAdapt 标注为"1.8k★ 早期项目"。本次源码级调研修正：其 `openadapt-flow` 引擎具备 fail-closed 门禁、对抗故障基准、哈希链台账、治理修复生命周期等**生产级工程纪律**，成熟度显著高于 star 数印象；早期的是其 legacy 单体（已冻结到 `legacy/`）。借鉴价值按生产级评估。

## 2. 三代架构演进

### 2.1 Alpha（2023-2024）：三段管线 + 策略模式

```
RECORDING（截图+输入事件）→ ANALYSIS（tokenize 给 LMM）→ REPLAY（按策略回放）
```

legacy 单体实现：`record.py`（1,653 行）/ `replay.py` / `models.py`（1,217 行）/ `events.py`（982 行聚合）/ `strategies/`（naive 直放、stateful GPT-4+窗口数据、vanilla 每步 VLM、visual FastSAM 分割）/ `adapters/`（anthropic/openai/replicate）/ `privacy/`（Presidio 脱敏）。

策略模式核心（`legacy/openadapt/strategies/base.py:17-127`）：`BaseReplayStrategy.run()` = 死循环 `截图 → 活动窗口事件 → get_next_action_event()（抽象）→ playback.play_action_event()`；已含 `prompt_is_action_complete()`（:140-176）——用 LLM 判"上一步完成没有，期望状态是什么"，是效果验证的思想雏形（当时成本高，`CHECK_ACTION_COMPLETE=False` 默认关）。

### 2.2 过渡（2024-2025）：冻结单体 → meta-package 拆分

拆为 capture / privacy / ml / retrieval / grounding / evals / viewer 七个可选包 + 统一 CLI；确立 **policy/grounding 分离**（"做什么"与"在哪做"两个模型各司其职）与 Set-of-Mark 标注。

### 2.3 现代（2025+）：受治理的演示编译器（canonical）

```
Human demonstration → Surface recorder → openadapt-flow compiler
  → Inspectable bundle → Qualification/certification → Governed runtime
  → Independent effect verifier → VERIFIED / HALTED / reconciliation
```

`architecture.md` 定义的五条产品级铁律：

1. **健康执行零模型调用**："A healthy run uses the compiled program and retained evidence. It makes no generative-model call."——LLM 只在编译期与（可选的）修复提案期出现，运行热路径 $0。
2. **前后双向核查**：动作前查活状态（pre-state），动作后查声明效果（post-action declared result）。
3. **效果验证独立于执行面**：验证读的是系统台账（FHIR/REST/SQL/文件），永远不是屏幕。
4. **修复提案≠授权**："An optional model can propose a repair when policy permits it. The proposal is not authorization."——修复必须走版本化评审晋升。
5. **数据边界 fail-closed**：原始录制默认不出本机；衍生品过界需"本地脱敏 + 完整清单 + 人工评审 + 精确哈希批准 + 目的地策略检查"五道。

## 3. 抽象阶梯（Abstraction Ladder）——演示到程序的理论骨架

| 层级 | 表示 | 变换 | 状态 |
|---|---|---|---|
| L0 Literal | 原始按键/坐标 | 无（采集） | **已实现** |
| L1 Symbolic | 聚合动作（`type "hello"`） | 事件归并 | **已实现**（capture events.py） |
| L2 Template | 参数化（`type "<greeting>"`） | 正则抽取 | 部分 |
| L3 Semantic | 意图级（`greet user`） | LLM 意图识别 | 研究 |
| L4 Goal | 任务描述 | 过程挖掘 | 未来 |

各层价值表（architecture-evolution.md §2）：Literal=精确回放/审计；Symbolic=可读日志；Template=**同任务不同数据**（正是 WT 的运行参数占位符做的事）；Semantic=跨应用迁移；Goal=自然语言控制。

**对 WT 的定位**：WT 的流程模型天然处于 L1.5-L2（录制转换器做聚合+参数提升），Airtest 式语义兜底在 L3，Agent 自然语言在 L4——OpenAdapt 证明"把 L0-L2 做扎实、L3+ 当研究"是正确的资源分配。
