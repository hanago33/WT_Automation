### 🔴 P0-2：运行收尾两行恒被判 ERROR（假红字）

**位置**：`WT_AUT_recorded.py:593`（`_log_run_end_banner`）、`wt_run_reporting.py:154`

两处均为 `log_step(单参数)` 调用，级别由 `detect_level()` 按文本猜测。

**实测证据**（字符串层面）：

```
level=ERROR  tag=error  | ========== 运行结束 · 状态=成功 · … · 成功 16 / 失败 0 ==========
level=ERROR  tag=error  | 运行结果摘要已写入: status=success, …, failed=0, …
level=ERROR  tag=error  | ========== 运行结束 · 状态=失败 · … · 成功 1 / 失败 15 ==========   ← 仅这条应为红
```

**端到端复现（决定性证据）**：审查者调用**真实的** `WT_AUT_recorded._log_run_end_banner()`，
传入符合 `wt_run_reporting.start_run_report()` 结构的成功报告（`failedCount: 0`），
捕获它**实际写出的日志行**：

```
[2026-09-17 11:37:26.129] [ERROR] ========== 运行结束 · 状态=成功 · 用时 123.4s · 步骤 16 步 · 成功 16 / 失败 0 ==========
```

对照失败运行（`failedCount: 15`）输出：

```
[2026-09-17 11:37:26.129] [ERROR] ========== 运行结束 · 状态=失败 · 用时 9.9s · 步骤 16 步 · 成功 1 / 失败 15 ==========
```

**两条完全同级（均为 ERROR）**。这不是推断 —— `[ERROR]` 是 `format_line()` 在写入时定下的级别 token，
即**线上日志文件里真实会出现这两行红字**。

#### 🔺 影响升级：P0-2 已扩散到新模块 `wt_log_query`（`464c621`）

审查期间实施会话新增了 `wt_log_query.py`（日志查询：级别/关键字/步骤过滤 + 摘要），
其 `level_of()` 对**无显式级别 token 的行**回退到 `wt_logging.detect_level()` —— 正是 P0-2 的根因函数。
实测后果：

| 场景 | 结果 |
|---|---|
| 新格式日志（成功运行 3 行） | 摘要 `共 3 行 · ERROR 1 · INFO 2` ← **成功运行被统计出 ERROR** |
| 老格式日志（成功运行 3 行） | 同样 `ERROR 1` |
| **用户选「ERROR 及以上」过滤** | **只返回那行「运行结束 · 状态=成功」** |

**这让 P0-2 从「视觉噪音」升级为「功能性误导」**：`wt_log_query` 的设计目的正是
「定位第一个出问题的步骤」（见其提交信息），而用户筛 ERROR 得到的却是运行成功的那行。

**测试盲区**：`tests/test_log_query.py` 有一个 `test_historical_success_line`，名字看似已覆盖此场景，
但它用的输入是一行**普通步骤日志**（`已通过流程链路匹配点击控件`），**不是真实的运行收尾行**：

| 输入 | `level_of()` |
|---|---|
| 测试用的假想行 | `INFO` ✅ |
| **真实收尾行**（`_log_run_end_banner` 实际产出） | **`ERROR`** ❌ |

即：该测试**恰好绕开了 P0-2**。33 项测试全绿，但覆盖不到这个真实场景。
→ 修 P0-2 时**建议同步补一条用真实 banner 文本的测试**。

**根因**：
- `_log_run_end_banner` 的 `extra` 段恒拼 `失败 {failedCount}`；而 `wt_run_reporting.py:67` 将 `failedCount` 初始化为 `0`，故**每次成功运行**的结束行都含「失败 0」。
- `wt_run_reporting.py:154-161` 的摘要行恒含 `failed=0`。
- `_BENIGN_ERROR_CONTEXT` 的豁免清单为 `('错误项','无错误','零错误','0 个错误','no error','0 error')`，**`失败 0` 与 `failed=0` 均不匹配**（已实测确认）。

**后果**：成功运行的日志结尾必然出现两行红字，使「日志里有没有红字」这一最直观的判断失效。讽刺的是 `_log_run_end_banner` 正是为了让人一眼分辨运行边界而引入的。

**修复**：两处显式传级别（结束 banner 按 `status` 传 `ERROR`/`INFO`，摘要行按其 `status` 字段传级别）；同时把 `失败 0`、`failed=0` 补入 `_BENIGN_ERROR_CONTEXT` 作兜底。

## 五、专章：日志面板永久冻结（跨会话交叉验证）

**此问题由另一并发会话（session-6）的 UI 审计报告提出，本审查独立复现确认。**

### 缺陷机制

`wt_server_monitor.py:14` 的服务端 `DEFAULT_TAIL = 300` 恒定返回最近 300 行；
`wt_task_queue_window.py:1891` 的 `_LOG_MAX_LINES = 400`。

`_append_lines_incremental`（L1920-1940）的判定为：

```python
current = rendered_count()
if len(text_lines) > current:      # ← 等长位移时恒为假
    for line in text_lines[current:]:
        widget.insert(...)
```

当控件渲染满 300 行后，日志继续增长时服务端仍返回 300 行（内容整体位移一行），
`len(text_lines) > current` 恒假 → **不追加任何内容**；
又因 `LOG_MAX_LINES(400) > SERVER_TAIL(300)`，trim 永不触发 → **永久冻结**。

### 独立复现结果

**（a）真实 `tk.Text` 控件复现（决定性证据）**：审查者直接调用**真实的**
`TaskQueueWindow._append_lines_incremental()`（未复制逻辑，仅借壳调用），
喂入服务端 `tail=300` 的等长位移快照：

| 轮次 | 服务端行数 | 控件显示行数 | 控件末行 |
|---|---|---|---|
| 1 | 300 | 300 | `第 299 行` |
| 2 | 301 | 300 | `第 299 行` ← **卡住** |
| 3 | 302 | 300 | `第 299 行` |
| 4 | 303 | 300 | `第 299 行` |
| 5 | 304 | 300 | `第 299 行` |
| 6 | **305** | 300 | **`第 299 行`** |

最终：服务端真实最新行 = `第 304 行`，**控件实际显示末行 = `第 299 行`**。
面板从第 2 轮起不再更新，此后**永久冻结**。

**（b）模型仿真**（早期验证，与 (a) 结论一致）：服务端 305 行时控件仍显示第 299 行。

```
轮 1：服务端共 300 行，tail 视图 300 行 -> 追加 300 行，控件 300 行
轮 2：服务端共 301 行，tail 视图 300 行 -> 追加 0 行，控件 300 行，最新='第 299 行'
...
轮 6：服务端共 305 行，tail 视图 300 行 -> 追加 0 行，控件 300 行，最新='第 299 行'
服务端真实最新行 = '第 304 行'   控件实际显示 = '第 299 行'
*** 控件已冻结：日志继续增长但面板内容不再更新 ***
```

### 影响面与逃生口（细化）

| 面板 | 数据源 | 冻结后能否恢复 |
|---|---|---|
| `monitor_log_text`（**运行日志** 页签，默认自动轮询开启） | `/api/logs?tail=300` | ❌ **无任何逃生口** —— `_clear_log_text`（L1738）只清 `log_text`，全仓**没有**任何地方重置 `_monitor_log_rendered_lines` |
| `log_text`（终端控制台） | `/api/tasks/<id>/logs?tail=300` | ⚠️ 可点「清屏」按钮（L672 → `_clear_log_text`）重置 `_log_rendered_lines = 0`，使下一轮轮询走全量重绘而暂时恢复 |

**严重度**：运行日志页签是用户远程监控运行进度的主界面。主日志为追加式，每步写数行，累计 300 行约对应 50~75 步 —— **111 步的长流程必然触发，且触发后无法恢复**（除非关闭重开窗口）。

### 与本次改动的关系（重要）

- **该缺陷在 `main` 上已存在**，不是 session-5 引入（`main` 已有 `_LOG_MAX_LINES = 400` 与 `_append_lines_incremental`）。
- 但本次改动与之有两处**耦合**，建议一并处理：
  1. `WT_AUT_recorded.py:322` **新增**了 `MonitorWindow.LOG_MAX_LINES = 400`，把同一个问题常量复制到了新模块；
  2. `tests/test_log_lifecycle.py` 新增 `test_cap_matches_queue_window_for_consistency`，**断言两处 400 必须相等**。

**关于该断言的精确影响**（此处修正本文档初稿的措辞）：它**不构成修复阻碍** —— 把两处上限**同步**降到 `<= 300` 时等式仍成立，测试照样通过。它的实际作用是**强制两处常量同步变更**：只改一处会失败。考虑到现在共有 3 个地方引用该数值（`wt_task_queue_window._LOG_MAX_LINES`、`WT_AUT_recorded.MonitorWindow.LOG_MAX_LINES`、该断言），修复时需一并调整。

**建议**：修复冻结缺陷时，上限应取 `<= SERVER_TAIL(300)`；更稳妥的做法是让控件上限**由服务端 tail 派生**（而非各自硬编码），从根上消除这类不一致。

- 行缓冲 `self._log_all_lines` **独立于 Text 控件**保存 —— 切换过滤条件时能重新筛选**全量**行，而不是只筛当前可见的那些。这是本功能最容易做错的地方，实施会话做对了。
- 所有对 `log_text` 的访问都走 `getattr(self, "log_text", None)` 并有 `None` 守卫 —— 过滤条在 `log_text` 控件创建**之前**构建（L5390 早于 `text_frame`），守卫是必要的，且已验证有效。
- `_append_log` 依赖 `self._log_all_lines`，该属性在 `__init__` 的 L1857 创建；全仓 26 处 `_append_log` 调用点**全部在 L3238 之后**，无初始化顺序问题。
- 载入行数由 15 提到 300，并在重载入前清空缓冲 —— 避免了重复调用时旧行累积。
- 设计约束「不 import tkinter（会被 CLI 与 headless 流程导入）」在 `wt_log_query.py` 中确实成立，且有对应测试断言。

**已核查澄清 —— P3 的 2000 行缓冲与冻结缺陷的关系**：

`WT_Launcher` 内有两个不同的日志面板，容易混淆，此处澄清：

| 面板 | 类 / 位置 | 数据源 | 渲染方式 | 是否受冻结缺陷影响 |
|---|---|---|---|---|
| 总控台「运行日志」页 | `LauncherApp`（`log_text` L5395） | **本地文件** `LOG_FILE`（`_load_recent_log`） | P3 新增的缓冲 + 增量插入 | ❌ **不受影响** —— 本地全量读取，不经服务端 tail |
| 服务器监视窗 | `ServerMonitorWindow`（`log_text` L1704） | `/api/logs?tail=300` | **`_render_logs` 每轮全量 `delete`+`insert` 重绘** | ❌ **不受影响** —— 全量重绘而非增量追加，绕开了 `len(text_lines) > current` 的等长位移失效 |

两个 `self.log_text` 分属**不同类**，无命名冲突。

**结论：P3 的 2000 行缓冲对总控台是有效的（本地文件，可完整拿到一次运行上下文）；

队列窗口「运行日志」页签（`_LOG_MAX_LINES=400` + `/api/logs?tail=300` + 增量追加）仍是冻结的。

> `ServerMonitorWindow`，且其为全量重绘），已在此更正。

**遗留问题**：

- ⚠️ **点击步骤时级别筛选未重置，会「点了却什么都没有」**（`WT_Launcher._filter_log_by_step`）。
