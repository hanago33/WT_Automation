## 0. 结论速览

**为什么复古**：本仓库 UI 约 735 处经典 `tk.*` 控件、仅约 86 处现代 `ttk.*` 控件。经典控件在
Windows 上直接映射为 Win32 原生子窗口（`tk.Button` → Win32 `BUTTON` 类），由 GDI 绘制、不参与
系统视觉样式——这就是"Win95 灰按钮"质感的来源。ttkbootstrap 主题引擎只能美化 ttk 控件，
对 90% 的经典控件无能为力，**装了现代主题却没有足够的现代控件可用**。

**为什么迟滞**：Tkinter 是单线程事件循环 + 同步布局求解 + 无 GPU 合成的 90 年代架构；本仓库
再叠加四个放大因素——巨型单类、刷新即全量重建、固定 120ms 轮询、日志区无限膨胀。
2026-09-09 第一轮优化（Tk 8.6.12 升级、滚轮路由、after_idle 合帧、grid_remove 模式切换、
队列窗口增量渲染）方向都对，但都属于"**减少无效功**"，没有触及"**经典控件 GDI 绘制 +
单线程同步布局**"两个本质，所以主观感受提升有限——这是架构天花板，不是手法问题。

**推荐路线（方案 A，主线）**：`tk.* → ttk.*` 全面迁移 + ttkbootstrap 2.2.2 深度应用 +
便携环境 Python 3.11 → 3.13（Tk 8.6.15），性能治理先行、外观分窗口分批替换、
每批有 816 项回归测试护栏；PySide6 重写保留为长期备选（新工具试点），不推荐整体迁移。

**工作量**：Phase 0–5 共约 7–10 个 worktree 会话，见 §6。

## 2. 原理层：Tkinter 为什么天生如此

> 本章解释"天花板"在哪，以及为什么第一轮优化无法突破它。除标注来源外，均为 Tk 架构的公开事实。

### 2.1 经典控件的绘制路径（复古感的根源）

- Tk 诞生于 1991 年（X11 时代），Windows 移植沿用"控件即子窗口"模型：
  `tk.Button` 在 Windows 上是真实 Win32 `BUTTON` 类子窗口，`tk.Entry` 是 `EDIT` 类。
- 经典 Tk 不携带 visual-styles manifest，这些 Win32 控件**不启用系统主题绘制**——
  渲染成 Win95 时代的灰色平面按钮。想靠 `bg=`/`relief=FLAT` 调教，也只能在 GDI
  纯色填充里打转：无圆角抗锯齿、无透明度、无过渡动画。
- `wt_theme.create_flat_button()`（`wt_theme.py:250`）已尽力用扁平配色 + Enter/Leave
  手动换色模拟现代按钮，但底层 `tk.Button`（`wt_theme.py:344`）决定了上限：
  悬停无渐变过渡、无圆角、DPI 变化时边缘生硬。

### 2.2 ttk 是 Tk 官方的现代化答案，但本仓库基本没用

- ttk（Tcl 8.5 引入）改为**全自绘**：统一 style 引擎（`ttk::style`）接管颜色/边框/
  hover 态/布局，不依赖 Win32 原生控件外观——这是 ttkbootstrap 能把 ttk 控件
  变成 Bootstrap 质感的原因。
- 本仓库统计（grep 精确计数，2026-09-11）：

| 控件 | 经典 `tk.*` | 现代 `ttk.*` |
|---|---|---|
| Button | 116（Launcher 55 + Editor 54 + Queue 7） | 3 |
| Label | 247 | 3 |
| Frame | 198 | 3 |
| Entry | 57 | 2 |
| Checkbutton | 25 | 2 |
| Radiobutton | 7 | 0 |
| LabelFrame | 51 | 0 |
| Scrollbar | 34（仅 4 处经 `create_modern_scrollbar` 包装） | 22 |
| Combobox / Treeview / Notebook / Progressbar / Separator | — | 51（ttk 独占） |

- 仓库唯一的主题入口 `WTThemeManager.init_theme(root, "flatly")`（`wt_theme.py:121`）
  已把 ttkbootstrap 挂载成功——**基础设施在，弹药（ttk 控件）没装**。

### 2.3 渲染与布局的架构限制（性能天花板）

- **单线程**：Tcl 事件循环串行处理输入、布局、绘制。任何一个 `configure()` 触发的
  重排都同步执行完毕才处理下一条用户事件——"点一下卡一下"由此而来。
- **布局求解**：pack/grid 每次 idle 周期对整棵控件树同步求解（`pack.n` packer
  算法，第一轮调研已核实原文：按 packing list 顺序分配 cavity）。深层嵌套 + 大量子
  控件时，一次 resize 逐级向上 propagate、逐级重算。
- **无合成器**：经典控件走 WM_PAINT/GDI 直接绘制到窗口表面，无离屏合成、无 GPU
  批渲染；Tk 8.6 仅 Canvas/ttk 有局部缓冲。窗口缩放时的黑闪/撕裂即此。
- **Python↔Tcl 桥**：每个 `widget.configure()` 是一次跨解释器调用；循环里逐控件
  configure 的代码在洪流场景下开销显著。

### 2.4 高 DPI 的双轨失配（排版/模糊问题）

本仓库 DPI 方案（`wt_dpi.py`）：`SetProcessDpiAwareness(2)`（:126）+ monkeypatch
`tk.Wm.geometry` 全局缩放尺寸（:179）+ `tk scaling` 缩放字体（:199）。这是
**像素缩放与字体缩放双轨并行**的人为拼合：字体按 scaling 增大，而 padding/边框/固定
尺寸要靠 `wt_dpi.scale()` 手工放大——任何一处漏调就是失配（对不齐、被裁剪）。
Tk 8.6 无内建 per-monitor 自适应；Tk 9.0 官方变化清单写明
"**Scaling-aware widgets and themes with SVG support**"（Tcler's Wiki
《Changes in Tcl/Tk 9.0》页），这是根治方向（见 §5 Phase 5）。

## 3. 代码层诊断（证据清单）

### 3.1 体量与巨类

| 文件 | 行数 | 说明 |
|---|---|---|
| `WT_Flow_Editor.py` | 10,726 | 8 个对话框类 + `FlowEditorApp`（:5570 起，单类约 5,150 行、2,894 处 `self.`） |
| `WT_Launcher.py` | 9,179 | 总控台单文件，Simple/Advanced 双模式全在一个类 |
| `wt_task_queue_window.py` | 2,966 | 队列窗口（已有增量渲染先例） |
| `WT_AUTOMATION_Agent/gui.py` | 2,899 | Agent 界面——实为本地 HTTP 服务 + 浏览器 Web UI（`http.server`），**非 Tkinter，不在本迁移范围** |

巨类不是性能问题本身，但使每次"再优化一点"的回归面都很大，是治理顺序必须
考量的结构约束（对应 Phase 6 拆分）。

### 3.2 轮询模型（操作迟滞的直接来源）

| 位置 | 周期 | 用途 | 问题 |
|---|---|---|---|
| `WT_Launcher.py:1989` 启动 → `:6825` 自续期 | 120ms | 子进程 stdout 队列轮询（单链：启动一次后每次轮询末尾 `after(120)` 自续） | 空转期无退避（队列无数据也 120ms 醒一次）；失败无退避策略 |
| `wt_task_queue_window.py:281-282` | `POLL_MS` ×2 | 服务器任务轮询 + 监控轮询 | 失败已有 2→4→8→16→30s 退避（`:2923`），空转期无退避 |
| `WT_Launcher.py:8073-8356` | 1200–1600ms | 子进程启动状态检查 | 串行 `after` 链，每跳一次全量回调 |

子进程 stdout 已用 reader 线程 + queue.Queue 解耦（方向正确），但消费端是定时轮询
而非事件驱动：`after(0, callback)` 机制已存在（`WT_Launcher.py:1759`），说明事件式
投递可行，只是没有全面铺开。

### 3.3 全量重建式刷新（渲染性能的直接来源)

- **步骤列表**：`_render_flow_step_list()`（`WT_Launcher.py:7050`）先
  `child.destroy()` 全部再逐个重建 `tk.Checkbutton`——每次刷新 = 全部控件销毁 +
  Win32 窗口重建 + 布局求解 + GDI 绘制。对比：队列窗口已有 `_append_lines_incremental`
  行级 diff 渲染（`wt_task_queue_window.py:1898` 起，配 9 项专项测试）——**同仓库内
  已验证的正确模式，Launcher 没有复用**。
- **日志区**：`WT_Launcher._append_log()`（:5522）每行一次 `insert` + `see(END)`，
  **无行数上限**（队列窗口有 `_LOG_MAX_LINES=400`，Launcher 没有）。Text 是行块
  B-tree，行数无限增长后 insert/see 越来越慢；高频日志流程（多塔队列）运行越久
  总控台越卡。
- **模式切换**：已治理（`grid_remove` + `tk busy`，`WT_Launcher.py:2136-2162`），
  但收尾仍是一次全窗 `update_idletasks()`——Simple 面板数百控件的同步重排。

### 3.4 排版：无集中样式的必然结果

`_build_ui()` 起手就是逐控件手写 `font=("Microsoft YaHei UI", 16, "bold")`、
`padx=16, pady=14`（`WT_Launcher.py:1993-2015`），全文 `padx=/pady=` 数百处。
没有单一来源的 spacing scale，视觉一致性完全靠手抄；ttk 的 style 机制本可
一次性定义（`style.configure("Card.TFrame", padding=...)`）。

### 3.5 已优化项盘点（第一轮成果，全部保留，不在本规划重复做）

| 优化 | 位置 | 状态 |
|---|---|---|
| Tk 8.6.12 + 触控板余数池滚轮路由 | `wt_wheel_router.py` | ✅ 已验证 |
| Canvas scrollregion after_idle 合帧 | `WT_Launcher.py:4824`、`:2570` | ✅ |
| 模式切换 grid_remove + tk busy | `WT_Launcher.py:2056-2162` | ✅（仍有残余黑影感，见 3.3） |
| 队列窗口增量渲染 + 行数上限 | `wt_task_queue_window.py:1898-1966` | ✅ 配 9 项测试 |
| 分割条平滑预览防抖 | `WT_Flow_Editor.py`（commit 1b070e0） | ✅ |

## 5. 推荐路线总览（方案 A + E 内嵌）

```
Phase 0 基线度量 ──→ Phase 1 性能治理(无视觉变化) ──→ Phase 2 ttk 迁移与主题集中
                                                        │
              Phase 4 视觉精修 ←── Phase 3 便携环境升级 3.13(Tk 8.6.15)
                                                        │
                              Phase 5(可选) Tk 9 试点 ──→ Phase 6(长期) FlowEditor 拆分
```

排序逻辑：
1. **性能治理先行**（Phase 1）：全部是无视觉变化的纯改善，趁控件未迁移时做，
   迁移后每项都要在两套控件上重验——先做省一半工作量。
2. **ttk 迁移按窗口分批**（Phase 2）：单窗口单 commit，816 项测试 + 视觉冒烟护栏。
3. **环境升级独立成相**（Phase 3）：便携 zip 替换涉及内网停机窗口，与代码解耦。
4. **Tk 9 押后**（Phase 5）：9.0.x 仍在修复期，ttkbootstrap 适配刚落地，用试点分支
   验证而非直接上生产。

## 6. 分阶段执行计划

> 每阶段 = 1+ 个 worktree 会话；每功能单元一 commit（AGENTS.md 规范）；阶段完成
> 即通知人类审查合并。所有性能数字以 Phase 0 脚本口径为准，禁止"感觉变快了"式验收。

### Phase 0 · 基线度量与冒烟基建（约 0.5 会话）

**目标**：为后续每一步提供可对比的硬数字；不改任何现有行为。

改动（全部新增，不触碰现有文件逻辑）：
- 新增 `tools/ui_perf_baseline.py`：自动计时冷启动→可交互、Simple↔Advanced 连续切换
  10 次、步骤列表刷新、日志洪流（灌 5,000 行）后的 insert 延迟；结果落
  `logs/ui_perf/baseline_<date>.json`。
- 手工冒烟清单文档化：三档 DPI（100%/125%/150%）截图基线存 `docs/08-数据与资产/ui基线截图/`
  （截图不入 git，按 AGENTS.md 不提交大产物，仅本地留存）。

验收门槛：脚本可重复运行（变异系数 <10%），基线表落档。

### Phase 1 · 性能治理（1–2 会话，零视觉变化，纯收益）

## 附：为什么不是"换框架就完事"（给未来会话的防跑偏备忘）

第一轮调研与本次复核一致表明：网文里"Tkinter 不行换 Qt/Flutter/Web"的叙事缺少
一手迁移案例支撑；而本仓库实测里，**还没用满 Tk 自带的现代化能力**（ttk + 主题
引擎只覆盖 10% 控件）。方案 A 的本质是"先把已付费的现代化能力用满、用可回退的
小步替换"，把"是否换框架"的决策推迟到证据充分时（Phase 5/新工具试点）再做。
这符合本仓库一贯的"重大决策不基于网文"原则（见 2026-09-09 调研 §6）。

### A.2 T2 · Launcher 日志限行 + 批量插入

- **目标**：`_append_log` 不会随流程运行越跑越卡；高频日志不再逐行刷 UI。
- **改动范围**：`WT_Launcher.py` 的 `_append_log`（:5522）+ 类属性区（加
  `_LOG_MAX_LINES = 400`）。允许新增 1 个辅助方法 `_flush_log_batch`。
- **参照代码**（先读再写）：
  - `wt_task_queue_window.py:2745` `_append_log_text` ——限行 trim 的成熟写法，
    注释里写明了 Tk `end-1c` 行号比真实行数大 1 的坑，照抄该算式；
  - `wt_task_queue_window.py:1898` 起的增量渲染区——行数上限共用逻辑。
- **实现规格**：
  1. 每行 append 先入 `self._log_pending: list[tuple[str, str]]`（(text, tag)）；
  2. `after_idle` 或 `after(50)` 定时 flush：`log_text.insert` 用
     `"\n".join()` 一次插入（tag 按 `Text.tag_add` 分段补），随后统一
     `see(END)` 一次；
  3. flush 后执行与参照代码相同的超行 trim；
  4. ⚠ 仅当滚动条位于底部（`self.log_text.yview()[1] >= 0.999`）才 `see(END)`，
     用户上翻查看历史时不强拉到底——这是高频日志下最影响体验的行为；
  5. ⚠ flush 前 `config(state=NORMAL)`、后 `config(state=DISABLED)` 成对出现，
     异常路径也不能漏 DISABLED（参照代码的结构）。
- **验收**：T1 场景③ 重测 P95 降 ≥50%；`pytest tests/ -q` 全绿；肉眼冒烟——
  跑一次 Simple 流程，日志滚动平滑、上翻不被拽回。
- **回退**：单方法改动，revert 即回旧行为。

- **改动范围**：`WT_Launcher.py` 的 `_render_flow_step_list`（:7050）及其调用方
  传入不变。新增实例字典 `self._step_row_widgets: dict[str, Checkbutton]`。
- **参照代码**：`wt_task_queue_window.py:1898-1966` `_append_lines_incremental`

  可对照学习断言风格）。
- **实现规格**：

### A.4 T4 · 轮询空转退避

- **目标**：stdout 队列空转期不再 120ms 空醒。
- **改动范围**：`WT_Launcher.py` `_poll_output_queue`（:6812–6825）单方法。
- **参照代码**：`WT_Launcher.py:4077`（本文件！Simple 远程轮询的失败退避，
  2→4→8→16→30s 封顶）与 `wt_task_queue_window.py:2923` 注释——两者即仓库
  收敛策略，照抄结构。
- **实现规格**：
  1. 实例属性 `_poll_idle_streak = 0`；队列取空 + 无 exit → streak+1；取到

# 附录 B · tk → ttk 转换对照表与踩坑清单

> 执行 T6–T15 时的唯一替换依据。左列 = 现有写法（grep 得到的真实形态），右列 =
> 等价 ttk 写法。"⚠ 坑"列是必须逐处核对的行为差异。

| 现有（tk） | 替换为（ttk） | ⚠ 坑（必须核对） |
|---|---|---|
| `tk.Button(bg=X, fg=Y, activebackground=Z, relief=tk.FLAT, bd=0, padx, pady)` | `ttk.Button` + style（见 T6） | `bg/fg/activebackground/bd` **不存在**，配置进 style；遗漏会抛 TclError，启动即发现 |
| `tk.Button(...).config(state=tk.DISABLED)` | `.config(state="disabled")` | ttk 也接受 `"disabled"` 字符串；`tk.DISABLED` 值就是字符串，兼容 |
| `tk.Label(bg=X, fg=Y, font=..., anchor=..., justify=...)` | `ttk.Label` + style 或直接无 style | `bg=` 必须删；文字色用 `foreground=`（ttk 接受）；`anchor/justify/font/wraplength` 直接兼容 |
| `tk.LabelFrame(text="  X  ", bg=..., fg=..., bd=1, relief=SOLID)` | `ttk.Labelframe` | 标题文字色/字体用 `style.configure("WT.TLabelframe", ...)`；`bd/relief` 换 `borderwidth`；标题前后空格排版会变，视觉核对 |
| `tk.Checkbutton(..., variable=var, bg=...)` | `ttk.Checkbutton` | `variable` 兼容；`bg` 删；`anchor/justify` 兼容 |
| `tk.Entry(..., bg=, fg=, insertbackground=, relief=FLAT)` | `ttk.Entry` | 校验红框等动态改边色的逻辑（如有）改用两个 style 切换；只读态 `state="readonly"` |
| `tk.Frame(bg=X)` | `ttk.Frame` + `style.configure(bg)` 或保留 tk.Frame | **Frame 可保留**——ttk.Frame 默认透明背景继承，混用最易出"灰块"。无边框纯容器建议保留 `tk.Frame`（本规划允许，不计入未替换） |
| `tk.Radiobutton` | `ttk.Radiobutton` | 同 Checkbutton |

**踩坑总表（T8+ 每批自查）**：
1. `winfo_children()` 遍历中 configure 子控件——ttk 与 tk 行为一致，无需改；
2. `widget.cget("bg")` 取色做联动的代码（grep `cget("bg")` 提前发现）——ttk 返回
   style 层级值，联动逻辑改从 palette 取；
3. 截图叠加框选/高亮 overlay 全是 Canvas/Toplevel——**不在替换范围**，别碰；
4. `messagebox` 是模块级函数，非控件，不受影响；
5. 每批跑完 `grep -n "tk\.\(Button\|Label(\|Checkbutton\|Entry\|Radiobutton\|LabelFrame\)" <file>`
   归零（LabelFrame 用 `tk\.LabelFrame`）——数量对得上才算完成。
