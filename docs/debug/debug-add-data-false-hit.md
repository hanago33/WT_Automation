# [OPEN] add-data-false-hit

## 背景
- 症状：`step_27` 日志显示“已通过父窗口相对区域点击”，但用户观察到实际没有点到“添加到数据”按钮，流程却继续进入 `step_28`。
- 后续 `step_29` 也失败，说明 `step_27` 可能存在假命中，导致后续上下文不符合预期。
- 目标：先确认 `step_27` 的点击是否真的发生在正确父窗口、正确区域、正确按钮状态上，再决定修步骤配置还是收紧成功判定。

## 本轮假设
1. `step_27` 的相对区域坐标本身偏了，日志记录的是点击动作成功，不代表业务按钮被命中。
2. `step_27` 点击时父窗口矩形与取点时不同，导致相对区域换算后的绝对坐标落到了错误位置。
3. `step_27` 点击后窗口或容器发生切换，但当前成功日志仍按第一次点击落点输出，掩盖了实际无效点击。
4. `step_27` 的成功条件过宽，只要执行了鼠标点击就记成功，没有校验点击后 UI 状态是否变化。
5. `step_29` 失败不是独立问题，而是 `step_27` 假命中后没有进入正确界面状态的连带结果。

## 调试计划
1. 读取 `step_26-step_29` 当前定义，确认 `step_27` 和 `step_29` 的父窗口/相对区域配置。
2. 仅在相对区域点击链路中为 `step_27` 和 `step_29` 增加最小插桩，不先改业务逻辑。
3. 让用户复现一次 `step_26 -> step_27 -> step_28 -> step_29`，读取 ndjson 后再决定修复点。

## 运行时证据
- `step_27` 的 `before` 事件显示点击前前台窗口就是 `导入时间序列文件 | Window | WPF`，其矩形为 `115,25,2444,1490`。
- 但 `step_27` 的 `before_click` 事件里，真正参与相对区域换算的窗口却变成了无标题主窗口 `Window_Main | Window | WPF`，矩形为 `0,0,2560,1516`，最终点击点落在 `(2304,1461)`。
- 运行报告 `wt_run_20260701_180151.json` 也同步证明了这一点：`step_27.extra.relativeRegion.windowTitle` 为空，`windowRect` 记录的是主窗口，而不是“导入时间序列文件”弹窗。
- `step_29` 出现同样模式：配置要求父窗口为 `从时间序列计算`，但 `before_click` 里仍然按无标题主窗口 `Window_Main` 计算了相对区域。

## 结论
- 根因不是用户观察误差，而是相对区域点击链路错误地把无标题主窗口当成了目标父窗口。
- 现有窗口评分逻辑对“显式标题 + 空标题 WPF 窗口”放得过宽，导致主窗口能冒充 titled dialog。
- 当前已做最小修复：
  1. `find_flow_window_for_relative_region(...)` 先检查前台窗口，若它已满足父窗口规格则优先采用。
  2. `score_window_against_spec(...)` 仅允许前台窗口使用“空标题 WPF fallback”，非前台空标题窗口不再可用该兜底冒充目标弹窗。

## 下一步
1. 重新复现 `step_26 -> step_29`，确认 `step_27` 的 `windowRect` 是否回到“导入时间序列文件”弹窗。
2. 若 `step_27` 修正后 `step_29` 仍失败，再继续看它是未进入正确业务状态，还是其相对区域本身仍需微调。
